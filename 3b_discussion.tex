\section{Discussion\label{sec:discussion}}

The research questions examine where architectural signal resides and how a mapping model can use it. RQ1 compares what file representations encode before message passing, RQ2 adds file, member, and folder context and compares the folder gains with a directory-based rule, and RQ3 examines how the way a predictor consumes dependency neighbors changes what they contribute. This section considers the three together and states the conditions under which they hold.

\parg{Dependency information in file representations.}
RQ1~\ref{sec:rq1} compares file representations before the predictor exchanges information between linked files, so the results reflect the architectural information encoded in each representation. Node2Vec, which is learned from the dependency graph alone, without labels, gives the highest micro-F1 on six of the nine systems and the highest macro-F1 on five. On Lucene, JabRef, and Bash, its vectors exceed those learned from a degree-preserving rewired graph by $56$, $23$, and $34$ macro-F1 points without message passing, so they encode dependency structure beyond node degree. Fine-tuned UniXcoder improves over its zero-shot counterpart on every system. Since the zero-shot encoder receives no dependency signal, this shows that fine-tuning on dependency-derived pairs adds information beyond that of pretrained code representations alone. Dependency information can therefore provide useful architectural signal before a predictor combines information across dependency links, either by encoding graph position directly in Node2Vec or by adapting a contextual code representation through dependency-guided fine-tuning.

The usefulness of this signal varies with the relation between dependency structure and the reference architecture. Node2Vec's micro-F1 is lower on the three least homophilic systems, SH-3D, HDF, and TeamMates (Table~\ref{tab:datasets}), with a median of $56$ compared with $74$ on the remaining six. When dependencies frequently cross module boundaries, random walks may place files from different modules in similar structural neighborhoods, limiting the module-discriminating information available to Node2Vec. Homophily is computed from the reference mapping and is therefore unavailable before a mapping exists; it is used here to interpret the observed pattern, not to select a representation in practice.

Fine-tuned UniXcoder shows a different pattern on the low-homophily systems. Its median micro-F1 is $67$ on SH-3D, HDF, and TeamMates, compared with $68$ on the remaining systems. It exceeds Node2Vec by $11$ micro-F1 points on SH-3D and TeamMates, which combine low homophily with the highest average degrees, $\langle k \rangle$ of $23.43$ and $22.90$. In these systems, dependency neighborhoods may span several modules, while the code content represented by UniXcoder can provide complementary evidence within such mixed neighborhoods. HDF is the exception: Node2Vec remains ahead of \ft{} ($55$ versus $47$ micro-F1), although every representation performs comparatively poorly on this system.

The two representations without dependency information, Word2Vec and zero-shot UniXcoder, show no consistent ordering. Their weaker overall results reinforce that the advantage of Node2Vec and \ft{} is associated with dependency information rather than with the use of a graph embedding or a code encoder alone.

The RQ2 and RQ3 comparison concerns a different use of dependencies. While Node2Vec learns file vectors from unlabeled random walks, the neighbor-based predictors use dependency links while learning the mapping from the available labels. The results show that useful dependency information in an input representation does not by itself establish that this additional neighbor use will help: directed, typed HGT propagation lowers F1 on most systems, whereas GAT and the neighbor \mlp{} generally gain. The effect therefore depends on how the predictor represents and processes the neighborhood information.

\parg{Folder organization and architectural exceptions.}
The gains from adding folder nodes in RQ2 show that directory organization helps reproduce the reference mapping. However, extending a directory assignment is different from identifying files that depart from it. The directory analysis separates these cases by checking which errors of a directory-based baseline the learned model repairs and which correct predictions it damages (Section~\ref{sec:directory_errors}).

Lucene and HDF mainly illustrate the first case. Their directories are pure under the reference mapping, and directory-baseline errors occur where the immediate directory has no labeled examples. Correcting these errors shows that a model can recover an assignment when local supervision is missing. It gives little evidence about conflicts between directory structure and architecture. Bash has mixed directories and therefore presents a different problem. JabRef shows why the distinction matters: adding folder context improves overall accuracy while losing more correct predictions on directory-baseline errors than it gains.

A mapping tool intended to identify architectural exceptions should therefore be evaluated on files that depart from their directory assignment, alongside overall accuracy. A rule-based directory baseline using only the initial labels provides a useful reference, but its repair and damage rates must be interpreted separately: repair is measured among baseline errors, whereas damage is measured among correct baseline predictions. Recovering assignments in directories without initial labels is useful, but does not establish that a model can identify files whose module assignment conflicts with their directory.

\parg{Dependency neighborhood processing and self-training.}
RQ3 distinguishes dependency information encoded in file representations from its additional use during prediction. GAT and \mlp{} generally benefit from dependency neighbors, whereas HGT often loses performance. Gains with N2V and \ft{} show that dependency-informed initialization does not make neighbor access redundant. However, GAT and HGT differ in graph direction, relation typing, and attention formulation, so the comparison does not isolate why GAT performs better. Removing direction and relation types from HGT reduces much of the loss, but changes both together. That neighbors improve GAT and \mlp{} with W2V and \ft{}, whose inputs carry no dependency information, reinforces the RQ1 finding that dependencies provide signal beyond file content. These findings concern the evaluated file-level predictors, not the usefulness of dependency types in general or the folder- and member-aware configurations.

On most systems, dependency neighbors help or hurt the predictor under both training schedules. Self-training therefore does not explain the general difference between predictors. TeamMates is an exception: HGT propagation improves macro-F1 under supervised-only training but lowers it under self-training. Equal training duration controls the epoch budget, but models can still acquire different pseudo-labels and follow different training paths.

A benefit from neighbors must also be distinguished from a benefit from self-training. On Chrome, \mlp{} benefits from neighbors under both schedules, yet self-training lowers its macro-F1. More broadly, self-training often lowers macro-F1 without a comparable change in micro-F1. Confident pseudo-labels may disproportionately reinforce large modules, but establishing this explanation requires examining which labels are added and how errors develop within each module.

\parg{Connectivity and neighbor information.}
Connectivity describes how much neighboring context is available, while homophily describes whether linked files share a module. Connectivity matters particularly for shallow message passing, whose reach is limited by the number of layers. Sparse neighborhoods restrict the features available for aggregation, whereas Node2Vec can encode more distant context through random walks. Connectivity can therefore constrain additional message passing even when the initial structural representation remains useful.

The N2V exceptions for GAT and \mlp{} occur on Bash and HDC, the systems with the lowest average degree. This is consistent with limited local context reducing the benefit of neighbor aggregation, but does not establish connectivity as the cause. In contrast, T.Mates and SH-3D have low homophily but among the highest average degrees, and they are the systems where file-level message passing significantly raised N2V micro-F1 in RQ2. HDF has similarly low homophily but a much lower degree and no comparable gain. These observations suggest that connectivity is relevant to the context available for shallow message passing, but with nine systems and correlated descriptors we cannot separate connectivity from homophily, system size, or label scarcity, and we did not test this.

\parg{Implications for evaluating mapping models.}
Evaluation should establish what the input representation already provides, then isolate neighbor access within a fixed predictor and training schedule. Comparing a graph model with a graph-free MLP changes both the predictor and its access to structure; switching neighbors on and off within the same predictor tests whether that access helps.

Macro and micro F1 scores should be read together, since correctly mapping more files does not necessarily improve performance across modules. The directory analysis adds a further requirement: aggregate scores should be accompanied by evidence about files that depart from directory-based assignments. Together, these comparisons distinguish the contributions of input features, neighbor processing, and training schedule, while exposing limitations hidden by aggregate scores.These points concern the nine systems and the compared configurations and do not rank the signals or the predictors in general.
