Title-- What Carries Architectural Signal? A Code-to-Architecture Mapping Study

Abstract--Assigning source files to reference architecture modules supports conformance checking and system understanding. Identifiers, code content, static dependencies, and directory organization inform this mapping, but their usefulness depends on how they are represented and processed. We investigate the contribution of file representations, folder and member information, and dependency neighbors, defined as files connected by static dependencies. We study nine Java, C, and C++ systems with limited labels, comparing Word2Vec, Node2Vec, and UniXcoder representations with feature-only and graph-based predictors. We vary file, member, and folder graph configurations and conduct controlled dependency comparisons under supervised-only and self-training schedules. Representations that encode dependencies provide strong feature-only baselines, while folder nodes yield the largest and most consistent gains among graph configurations. However, these gains largely reflect information available through a directory rule and do not consistently improve predictions for files that depart from it. With file representations held fixed, neighbor access improves a Graph Attention Network (GAT) and a multilayer perceptron (MLP) receiving each file's representation and the mean representation of its neighbors on most systems. In contrast, directed, typed Heterogeneous Graph Transformer (HGT) propagation reduces median macro-F1 on most systems. An undirected graph with a single dependency relation largely removes these losses. Useful dependency information therefore does not necessarily imply beneficial propagation. Evaluations should distinguish information already encoded in file representations from the contribution of neighbor access and assess directory-departing files separately from aggregate performance.

\section{Introduction\label{sec:intro}}

Maintaining a software architecture requires knowing which implementation elements belong to its modules. That correspondence can become difficult to maintain as a system grows: new files introduce responsibilities and dependencies, while architectural documentation may lag behind the implementation. Code-to-architecture (C2A) mapping addresses this problem by assigning source files to the modules of a reference architecture. The resulting mapping supports reflexion modeling, which compares implementation dependencies with architectural relations to identify divergence~\cite{reflexion1}. It therefore connects the modular decomposition used to reason about a system~\cite{parnas1972,clements2003} to the code in which that decomposition is realized.
 
Several sources of evidence can support a mapping. Identifiers express domain concepts and implementation roles. Contextual code representations capture information from declarations and operations. Static dependencies locate a file among other files with which it interacts, while directories record how developers organize the project~\cite{sarif,negar,garcia2013}. These sources need not agree: a utility may depend on several modules, terminology may be shared across responsibilities, and a directory may contain files assigned to different architectural modules.
 
The usefulness of an information source also depends on how it enters a predictor. A dependency embedding can encode graph structure before a classifier sees a file. Propagating over dependencies then supplies a second form of access to related files, with its own assumptions about direction, relation types, and aggregation. A gain from the embedding does not establish that this additional propagation will help. Similarly, a folder-aware model can improve overall agreement with a reference architecture while losing correct predictions for files that depart from a directory-based assignment. These distinctions motivate studying both the information supplied to a model and the changes caused by the way it processes that information.

Prior architecture recovery and mapping work provides several ways to represent these sources. NEGAR learns structural representations using Node2Vec random walks on the dependency graph~\cite{negar}; GAER used a graph autoencoder with Word2Vec identifier embeddings for recovery~\cite{gaer}; prior mapping work uses lexical and organizational features with graph convolutional networks~\cite{jabeen2025graph}. Later work compares random walk-based methods with graph attention and diffusion-based rewiring and examines alternative uses of dependencies and folders~\cite{structsar}. These studies generally fix the representation chosen for each source, so it remains unclear which signal provides the strongest architectural evidence and how it should be represented.

We study this question through C2A mapping, a prerequisite for reflexion modeling~\cite{reflexion1}. We formulate C2A mapping as a classification problem in which each file is assigned to one module of the reference architecture. We work in a low-label setting, where about 5\% of the files are already mapped, and the model infers the remaining assignments. The model is trained either on the labeled files alone or with self-training using its own confident predictions. This setting allows us to examine how file representations and graph relations contribute under limited supervision.

Our evaluation uses nine Java, C, and C++ systems and covers lexical Word2Vec, structural Node2Vec, and contextual UniXcoder representations. These serve as inputs to a graph-free neural baseline and to two graph neural networks (GNNs), a Heterogeneous Graph Transformer (HGT)~\cite{hgt} and, in the controlled comparisons, a Graph Attention Network (GAT)~\cite{gat}. The heterogeneous configurations contain file nodes and, where applicable, folder nodes and one aggregate member node per file. They vary both the context available to a file and where feature content is stored. We compare these file representations and complement the configuration comparisons with controlled comparisons that change one design choice while holding the features, labeled splits, initialization, and training budgets fixed within each comparison.
 
The configuration results motivate two complementary analyses. A directory analysis distinguishes errors corrected by a model from previously correct predictions that it makes incorrect. A dependency analysis first tests whether embeddings retain useful information beyond a degree-preserving rewiring control on three systems, then compares ways of using dependency neighbors on all nine systems. Both stages of the dependency analysis use supervised-only and self-training schedules of equal duration.

We address three research questions:
\begin{itemize}
    \item \textbf{RQ1.} How does mapping performance vary across lexical, structural and contextual file representations?
    \item \textbf{RQ2.} How does mapping performance change when those representations are used in file, member, and folder graph configurations?
    \item \textbf{RQ3.} How do graph representation, training schedule, and neighbor processing affect the contribution of structural context?
\end{itemize}

The results show that dependency information supports C2A mapping through both file representations and neighbor context, but the benefit of neighbor context depends on how it is processed. Folder organization yields the largest gains, largely reflecting information already available through a directory rule. Aggregate improvements can conceal regressions on individual files. These findings clarify how input signals and their use by a predictor affect C2A mapping across the nine systems studied\footnote{\label{fn:code}Code and data are available at \url{https://github.com/sse-lnu/hetmap}.}.

\section{Related Work\label{sec:work}}

Architecture recovery and code-to-architecture mapping both infer a system's modular structure from implementation artifacts, relying on evidence that includes static dependencies, code semantics, and directory organization, among other sources. Recovery produces a decomposition without a reference architecture, while mapping assigns entities to the modules of a given one. We evaluate C2A mapping, and draw on recovery research for representations of dependencies, lexical content and project organization. We organize this work by information source while keeping the two evaluation tasks distinct.

Architecture recovery techniques have historically been built around one dominant signal. Dependency-based methods treat the system as a graph and partition it to maximize modularization quality, using search-based optimization~\cite{bunch,bunch_sahc_nahc,dagc,wca,mca_eca} or clustering over dependency-derived similarity~\cite{cct,hcc_2019,limbo,fca,neighborhood_tree_2019,gma_2021}. These perform well when dependencies align with architectural boundaries, but recovery quality is sensitive to how the graph is constructed and how relations are weighted, since shared utilities and layered interactions introduce cross-module edges. Semantic methods instead cluster artifacts by identifiers and comments in a latent space learned from source code~\cite{arc,zbr,risi2012fold} or from lexical cues~\cite{kargar2017semantic}, and directory-based methods use file names and paths as an architectural signal~\cite{file_clustering}. Non-structural signals can be noisy in isolation because reused terminology and utility directories mix entities from many modules. Hybrid methods therefore combine sources through weighted similarity fusion and many-objective remodularization~\cite{sc_misra,escrc,nsga3,sadat2019multi}, consensus clustering~\cite{ensemble_recovery}, semantic-guided propagation~\cite{evol}, or weighted graphs with community detection~\cite{sade,sarif}, using different mechanisms to combine the available evidence.

Mapping shows the same pattern from a different starting point. Early work framed the assignment of unmapped entities as orphan adoption~\cite{tzerpos1997orphan}, and HuGMe introduced attraction functions to recommend mappings between entities and modules~\cite{christl2005equipping,christl2007automated}. Subsequent methods varied the signal and the learner: information-retrieval attraction based on textual similarity~\cite{bittencourt_IR}, supervised classifiers for orphan adoption~\cite{bibi2016supervised}, and a semi-supervised Naive Bayes approach combining lexical and dependency-derived information through Concrete Dependency Abstraction~\cite{olsson2019semi,olsson2022automatically}. Interactive and text-based approaches followed, comparing text classifiers for module assignment~\cite{florean2021textclassifierscomparison}, recommending mappings from natural-language architecture descriptions~\cite{InMap}, and integrating package- and class-level granularity~\cite{sinkala2023integrated}. More recent work frames method-level mapping as text classification over TF-IDF, GloVe, and LLM representations~\cite{johansson2024mapping}, examines how textual data properties condition embedding-based classification performance~\cite{johansson2025mapping}, and extracts architectural concepts from documentation and code~\cite{fuchss2025enabling}; LLM-based chain-of-thought prompting has also been used to map implementation units to a reference architecture~\cite{rukmono_deductive}, though such prompting-based approaches face scalability challenges on large codebases given context-size limits and the cost of repeatedly processing implementation artifacts.

Representation-learning approaches differ in both the information they encode and the operations used to recover or predict modules. NEGAR clusters node2vec embeddings from the dependency graph alone, with no node semantics~\cite{negar}. Jabeen et al.~\cite{structsar} build on this by adding folder organization and comparing node2vec, meta-path walks, and graph attention with and without diffusion rewiring, without lexical features. GAER and Jabeen et al.~\cite{gaer,arl_2026} instead fix folder and identifier tokens into one encoding, Word2Vec-based in the former and contrastively trained with edge attributes in the latter, without comparing it to alternatives. For mapping, prior work evaluated graph neural networks on homogeneous and dependency-type-aware graphs~\cite{jabeen2025graph}, without folder hierarchies, containment, member-level artifacts, or separating graph contribution from feature contribution. These approaches motivate our distinction between representing an information source and using it during prediction. Our configuration comparisons span lexical, structural and contextual inputs, but retain differences between their training procedures and feature content. We therefore complement them with matched dependency controls and directory-error analyses. These controls assess specific design choices; they do not turn the broader configuration comparison into an isolated ranking of information sources.

\section{Background \label{sec:background}}

Software artifacts are naturally relational and multi-typed. A system contains folders, source files or classes, and finer-grained program elements such as methods and fields, connected through relations that include folder containment, file-to-member composition, and static code-level dependencies such as calls, inheritance, type usage, and field access.
 
To preserve these distinctions, we represent each software system as a heterogeneous software graph $G=(V, E,\mathcal{A},\mathcal{R})$. Here, $V$ denotes the set of software artifact nodes and $E$ denotes the set of relations between them. Each node $v \in V$ is assigned a node type through the mapping function $\tau(v): V \rightarrow \mathcal{A}$, where $\mathcal{A}$ contains folder, file, and aggregate member types in our most detailed configuration. Similarly, each edge $e \in E$ is assigned a relation type through $\phi(e): E \rightarrow \mathcal{R}$, capturing folder hierarchy, the association between folders and classes, the association between classes and finer-grained program elements, and static code dependencies such as method calls, inheritance, and imports.
 
In this graph, the meaning of a relation is not characterized by the relation type alone. It also depends on the types of the source and target nodes that the edge connects. Therefore, for an edge $e_{s,t}$ from source node $s$ to target node $t$, we describe the typed interaction as a meta-relation $\langle \tau(s), \phi(e_{s,t}), \tau(t) \rangle$. For example, a $\langle \text{folder},\ contains,\ \text{file} \rangle$ relation captures project organization, whereas a $\langle \text{file},\ Import,\ \text{file} \rangle$ relation captures code-level coupling. Thus, the same graph can preserve both structural organization and implementation dependencies without treating them as identical relations. A homogeneous graph, with one node type and one relation type, discards this distinction, and RQ3 uses it to test whether the typed, directed form matters.
 
HGT~\cite{hgt} exploits such meta-relations during message passing by conditioning attention and message transformation on the source node type, edge type, and target node type. GAT~\cite{gat} also uses attention-based message passing, but its standard formulation does not explicitly distinguish node or relation types. HGT can also operate on a graph with a single node type and a single relation type, although this does not make its attention mechanism equivalent to that of GAT, and RQ3 compares both on such a graph. The initial node features determine what information is available to these models, so graph structure and feature representation describe different parts of a mapping model, even when both are derived from dependencies.
 
A lexical embedding trained on identifier tokens captures naming conventions but not a file's position within the dependency structure or the syntactic and behavioral content of its implementation. An embedding trained directly on the dependency graph, such as Node2Vec~\cite{node2vec}, instead encodes a file's structural neighborhood without reference to its content, and such embeddings have been shown to capture dependency-based cohesion effectively in architecture recovery~\cite{negar,structsar}.
 
Pretrained code encoders such as UniXcoder~\cite{unixcoder} address the content gap left by lexical features by learning general-purpose representations of source code from large corpora, but their pretraining objective is not specific to architectural grouping: two files can be lexically and syntactically similar while belonging to different modules. Contrastive learning offers a way to adapt such an encoder to a task-specific notion of similarity by training the model to place designated positive pairs closer in the embedding space than unrelated in-batch examples, typically through an InfoNCE objective~\cite{infonce}. Using positive pairs derived from dependencies encourages the embedding space to reflect dependency proximity. It does not guarantee that this proximity coincides with the reference modules.

\section{Methodology\label{sec:method}}

This section presents the methodology for studying how architectural signals and graph design choices affect code-to-architecture mapping. We formulate the mapping task as node classification over a software graph $G=(V, E,\mathcal{A},\mathcal{R})$, where $\mathcal{A}$ and $\mathcal{R}$ denote the sets of node and relation types. Let $V_f \subseteq V$ be the set of file nodes, which are the targets of the mapping task. A small subset $L \subset V_f$ is initially labeled with known architectural module assignments, and the remaining file nodes $U = V_f \setminus L$ are unlabeled. The objective is to learn an encoder:
\begin{equation}
Z = f_{\theta}(G), \qquad Z \in \mathbb{R}^{|V_f| \times d},
\end{equation}
that maps each source file $i\in V_f$ to a $d$-dimensional embedding $z_i$, where $\theta$ denotes the learnable parameters of the representation-learning method. These file embeddings are used to predict architectural modules and to infer the labels of the nodes in $U$.
 
We first describe the graphs and the structural, lexical, and contextual features used to initialize their nodes. We then present the graph-free MLP, the HGT encoder, and their iterative training procedure. RQ1 varies the file representation, using the graph-free MLP. RQ2 varies the graph configuration for each representation and compares the results with a directory baseline described in Section~\ref{sec:dir_predictor}. RQ3 fixes the representations and varies neighbor information, predictor, and training schedule, as described in Section~\ref{sec:controlled_setup}.

\subsection{Heterogeneous Graph Construction\label{sec:het_graph}}
We model the software system as a heterogeneous graph whose nodes represent software artifacts and edges represent organizational, containment, and dependency relations. The graph is built from three sources of information: the folder structure of the project, the containment of program elements within a file, and static dependencies extracted from source code. Folder structure provides organizational context, containment connects folders to the files they contain and members to the files they belong to, and static dependencies describe interactions between software entities. We preserve these sources as distinct node and relation types rather than collapsing them into a single homogeneous graph. Figure~\ref{fig:schema} illustrates the general schema of the heterogeneous software graph and the meta-relations used in our model.

\subsubsection{Node Types}
We use three node types: folder, file, and member. Folder nodes represent directory levels in the project structure. File nodes represent source files and are the target nodes for code-to-architecture mapping. Member nodes represent member-level program information associated with a file, including methods, fields, constructors, and variables.
 
We use one summarized \textit{Member} node per file rather than representing each method, field, constructor, or variable as a separate node. The member node aggregates lexical and dependency information from the members of its associated file, retaining member-level information while avoiding the large and sparse graphs produced by fully fine-grained representations.

\subsubsection{Relation Types}
The graph contains structural relations, including organization, containment, and dependency. Logical components are often implemented through namespaces or directory structures that group source code providing a particular functionality, and such structures reflect how developers organize files~\cite{fundamentals_sa, garcia2013}. To preserve this information, each directory level is represented as a separate folder node. Folder nodes are connected through \emph{parent\_of} edges, forming hierarchical chains such as \texttt{app} $\rightarrow$ \texttt{app/ui} $\rightarrow$ \texttt{app/ui/views}. File nodes are linked to their folder through \emph{contains} edges, and each member node is connected to its enclosing file through a \emph{belongs\_to} edge.

Static dependencies provide direct evidence of how entities interact and are a central source of information for architecture mapping and recovery~\cite{negar, deps_impact}. The frozen dependency artifacts were extracted with the Depends tool~\cite{depends}, which analyzes the syntactic structure of the projects studied in this paper and identifies entities together with several categories of static relations. Different dependency types can carry distinct architectural meanings~\cite {edge_weights, sarif}, so we keep them as separate relational edge types rather than merging them into a single dependency relation. \subsection{Node Feature Initialization \label{sec:node_features}}
We initialize node features based on the information source used in each experimental setting. Folder nodes are always initialized from binary folder-path tokens, regardless of which strategy is used elsewhere in the graph. File and member nodes are initialized using one of three strategies: lexical embeddings from Word2Vec, structural embeddings from Node2Vec, or contextual embeddings from UniXcoder, used zero-shot or fine-tuned with dependencies as described below.
 
\subsubsection{Folder Node Features}
 
Folder nodes are encoded using a binary bag-of-words representation over folder tokens. The folder tokens are derived from directory segments after removing common project-root tokens. Each folder node is represented by the tokens along its path in the directory hierarchy. For example, a folder corresponding to \texttt{app/ui/views} carries the tokens \texttt{app}, \texttt{ui}, and \texttt{views}. This allows deeper folder nodes to retain information about their hierarchical context.
 
\subsubsection{Word2Vec: Lexical Features \label{sec:node_w2v}}
Source code identifiers often encode domain concepts and implementation roles, making them useful cues for mapping entities to architectural modules~\cite{sarif}. We use Word2Vec embeddings following the approach of Jabeen et al.~\citep{gaer} for lexical input. Tokens are extracted from file names and member-level program elements, including methods, fields, constructors, and variables. We normalize identifiers by splitting camelCase, PascalCase, and snake\_case forms, converting tokens to lowercase, and removing stopwords and non-alphabetic tokens. The remaining tokens are represented using 128-dimensional skip-gram Word2Vec embeddings~\cite{word2vec}, trained for 20 epochs with a context window of five. Each node representation is computed by averaging the embeddings of its associated tokens.
 
The graph variant determines where these features are stored. In FFM and FM, the file node contains file-name tokens and the member node contains identifiers from the file's program elements. FF and F have no member nodes, so member identifiers are included in the file representation instead, and the graph-free MLP uses the same file vector as F and FF. Member identifiers therefore remain available in every variant, but moving to FM or FFM changes where the information enters the model as well as changing the graph and its parameters.
 
\subsubsection{Node2Vec: Structural Features \label{sec:node_n2v}}
Chen et al.~\citep{negar} observe that files in the same architectural module can occupy a dense local dependency region without being directly connected. Shallow message passing over raw dependency graphs can therefore provide too limited a context to expose such relationships, whereas random walks can capture longer-range dependency structure~\cite{structsar}. We use Node2Vec's~\cite{node2vec} random-walk embeddings as a structural initialization and merge all static dependency types into a single edge type before generating random walks. Its biased random walks use parameters $p$ and $q$ to balance local and exploratory walks. The resulting embeddings capture structural similarity from dependency position without using identifier text or folder location.
 
In FM and FFM, each aggregate member node receives the Node2Vec embedding of its corresponding file. These configurations therefore change graph processing without introducing a separately learned member-level structural embedding.
 
\subsubsection{UniXcoder: Contextual Features \label{sec:unixcoder}}
For contextual initialization, we use UniXcoder~\cite{unixcoder}, a pretrained code transformer. The zero-shot variant uses its pretrained weights directly. The dependency-guided variant fine-tunes the encoder separately for each system using that system's dependency structure.
 
Source files are parsed with tree-sitter~\cite{tree_sitter} to produce separate file and member views. For Java, the file view contains type headers, field declarations, and constructor signatures with short body excerpts. The member view contains ordinary method declarations and excludes constructors. C/C++ extraction uses the appropriate language grammars to separate type and state declarations, including applicable constructors, from ordinary operations. It preserves physical-file boundaries and does not expand includes or macros. Unlike Word2Vec, UniXcoder does not move the member text into the file view when member nodes are absent.
 
Jabeen et al.~\cite{structsar} show that shallow message passing over the raw dependency graph struggles to expose relationships between files that are connected only through shared neighbors rather than a direct edge. Therefore, positive pairs for contrastive fine-tuning are drawn primarily from the two-hop neighborhood: for each anchor file, two-hop candidates are ranked by the number of distinct one-hop neighbors shared with the anchor, and two pairs per file are sampled from the top eight candidates; files without any two-hop candidates fall back to a direct neighbor. Training uses an InfoNCE~\cite{infonce} objective with in-batch negatives; in-batch items connected by dependencies but not selected as a positive pair are masked so that they act as neither positive nor negative.
 
Only the upper four encoder layers are updated during fine-tuning, while the token embedding layer and the lower eight encoder layers stay frozen, since the number of dependency pairs available in a single system is small relative to the encoder's parameter count. Adaptation is performed independently for each subject system, as dependency structure and naming conventions are project-specific.
 
Member information therefore enters the model differently for each representation. W2V moves member identifiers from the file vector to the member node when member nodes are present, UniXcoder provides member text only through the member node, and N2V gives the member node the file's own vector. Moving from F to FM or FFM thus changes how information enters the model as well as the graph, and the comparisons across graph variants are interpreted for each representation separately.
% __________ Model ________________
\subsection{Mapping Models\label{sec:mapping_models}}
All models map the final file representation to module logits with a linear layer and are trained by minimizing categorical cross-entropy over the labeled file nodes. They differ in how that file representation is computed.

\subsubsection{Multilayer Perceptron (MLP)\label{sec:mlp}}
The MLP predicts module logits directly from a file-level input vector. Each hidden layer computes:
\begin{equation}
h_i^{(k+1)} = \text{ReLU}\big(W^{(k)} h_i^{(k)} + b^{(k)}\big),
\end{equation}
with $h_i^{(0)} = x_i$ the file feature vector and $W^{(k)}, b^{(k)}$ the learnable parameters of layer $k$, and ReLU is the rectified linear unit~\cite{relu}. After the final hidden layer, a linear layer maps the resulting representation to module logits. The input $x_i$ contains the single representation being evaluated.

\subsubsection{Graph Attention Network (GAT)\label{sec:gat_model}}
GAT~\cite{gat} is an attention-based graph neural network. It updates a node's representation through a weighted aggregation of transformed neighbor features, averaged across $K$ attention heads:
\begin{equation}
h_i^{(1)} = \mathrm{ELU}\!\left(\frac{1}{K}\sum_{k=1}^{K}\sum_{j\in\mathcal{N}(i)} \alpha_{ij}^{(k)} W^{(k)} h_j^{(0)}\right),
\end{equation}
where $\alpha_{ij}^{(k)}$ is the attention weight of neighbor $j$ for node $i$ in head $k$, $W^{(k)}$ is a head-specific learnable matrix, and $\mathrm{ELU}(\cdot)$ is the exponential linear unit~\cite{elu}.

\subsubsection{Heterogeneous Graph Transformer (HGT)\label{sec:hgt_model}}
Node types have different feature spaces depending on the graph variant and the initialization strategy, so the HGT-based model first maps each node type into a shared hidden space using a type-specific linear transformation followed by ReLU. One HGT layer~\cite{hgt} then updates node representations through multi-head attention over their neighbors. Attention uses target-type-specific query transformations, source-type-specific key transformations, edge-type-specific matrices, and a learned prior for each meta-relation. Messages use source-type-specific transformations and edge-type-specific matrices. These parameters allow a \emph{contains} edge from a folder and a \texttt{Call} edge from a dependent file to receive different attention weights. In our implementation, the aggregated messages are combined with the node's projected input through a residual connection followed by layer normalization:
\begin{equation}
h_t^{(1)} = \mathrm{LayerNorm}\left(\sum_{s \in \mathcal{N}(t)} \alpha(s,e,t) \cdot M(s,e,t) + h_t^{(0)}\right),
\end{equation}
where $\alpha(s,e,t)$ and $M(s,e,t)$ denote the attention weight and message from source node $s$ to target node $t$ over edge $e$, with attention-head indices omitted for brevity, and $h_t^{(0)}$ is the projected input. The residual connection retains a direct path from the initial node features~\cite{residual_connection}. Folder and member nodes, when present, contribute to file representations through message passing. 

% ________ Algorithm _____________
\subsection{Iterative Learning Framework\label{sec:iterative_learning}}
The configuration experiments use a common form of iterative self-training: predictions above a confidence threshold supplement the initial labels. The thresholds and maximum round counts differ across models, as detailed in Section~\ref{sec:exp_setup}. The controlled experiments additionally fix the training duration and include a supervised-only schedule.

Starting from the labeled set $L$, the model first trains in a supervised warm-up phase on $L$. It then scores every file node with a softmax over the predicted modules; the highest probability is the model's confidence in that prediction. In each self-training round, unlabeled file nodes whose confidence exceeds a threshold $\delta$ receive pseudo-labels and are added to $L_{\text{pseudo}}$, and the model is retrained on the union of the original and pseudo-labeled nodes. If a later round predicts a different label for a pseudo-labeled node with confidence above $\delta$, the pseudo-label is updated. The procedure stops when no new confident nodes are found, when fewer than five nodes were added in the previous round, or when the maximum number of self-training rounds is reached. The fixed-budget self-training schedule of the controlled experiments in RQ3 disables these early stopping conditions and completes all three rounds, including rounds with no new pseudo-labels.

\subsection{Experimental Configuration\label{sec:exp_setup}}

RQ1 and RQ2 use a low-label setting: a small subset of files has known module assignments, and the models predict the assignments of the remaining files. We repeat each experiment 100 times with a different initial labeled set. In each run, we randomly sample 5\% of the file nodes, with a minimum of 30 and a maximum of 200 files, and add one file from every GT module absent from the sample so that all modules are represented. All compared configurations use the same initial labeled set within a run, which allows paired comparisons, and the repetition measures sensitivity to which files are labeled. RQ3 uses separate controlled experiments, described in Section~\ref{sec:controlled_setup}.

We evaluate four file representations: Word2Vec (W2V), Node2Vec (N2V), zero-shot UniXcoder (\zs{}) and fine-tuned UniXcoder (\ft{}; Section~\ref{sec:node_features}). W2V uses 128-dimensional vectors trained on the file names and identifiers of each system (Section~\ref{sec:node_w2v}). N2V learns 128-dimensional vectors from random walks on the undirected file-level dependency graph (walk length 30, 200 walks per file, $p=q=1$, window 15, five skip-gram epochs and five negative samples). Chromium uses 100 walks per file and one negative sample. The N2V vectors are computed once per system and reused across runs. For \ft{}, UniXcoder is fine-tuned with an InfoNCE temperature of $0.05$, AdamW with a learning rate of $2\times10^{-5}$, a batch size of eight, and two epochs with a fixed seed. Both UniXcoder variants encode file inputs with a 512-token limit and member inputs in overlapping 256-token windows with a stride of 128, mean-pooled before normalization, producing 768-dimensional features. Graph structures follow Section~\ref{sec:het_graph}.

All mapping models are trained with Adam at a learning rate of $0.001$. They start with 100 supervised epochs and then use the iterative self-training procedure of Section~\ref{sec:iterative_learning}: pseudo-labels above a confidence threshold are added to the training set, and each round trains for 30 epochs. HGT and GAT use one layer, 256 hidden dimensions, four attention heads, and three self-training rounds with $\delta=0.95$. The MLP uses two hidden layers with 256 dimensions. Its W2V and \ft{} configurations use four rounds with $\delta=0.95$, whereas its N2V configuration uses three rounds with $\delta=0.90$.

All mapping models are trained with Adam at a learning rate of $0.001$. They start with 100 supervised epochs and then use the iterative self-training procedure of Section~\ref{sec:iterative_learning}: pseudo-labels with confidence above $\delta=0.95$ are added to the training set in three rounds of 30 epochs each. GAT and HGT use one layer, 256 hidden dimensions, and four attention heads, and the MLP uses two hidden layers with 256 dimensions.

% _______________ Directory Reference Predictor ________________
\subsubsection{Directory Hierarchy Baseline\label{sec:dir_predictor}}

To assess how much folder-based configurations exploit files in the same directory sharing a module, we use a rule-based predictor based on the directory hierarchy and the initial labeled files. For each unlabeled file, it assigns the most common module among labeled files in the same directory. If none are present, it searches the directory subtree and then the subtrees of its parent directories until it finds labeled files. Ties are resolved by the module's frequency in the complete initial labeled set and then alphabetically. If no labeled files are found, the predictor assigns the most common module in the complete initial labeled set. It uses the directory hierarchy, but not directory-name text, source code, embeddings, dependencies, or test labels.

We apply the predictor to the first ten initial labeled sets of the 100 runs and compare its predictions with FM and FFM predictions. A model \emph{repairs} a predictor error when it correctly maps a file that the predictor maps incorrectly. It \emph{damages} a correct predictor assignment when it incorrectly maps a file that the predictor maps correctly. We report the percentage of predictor errors repaired and the percentage of correct predictor assignments damaged. Because these percentages have different denominators, their difference is not a net change in accuracy. For analysis, we also record whether each directory contains initial labeled files and whether all files in a directory belong to one GT module. These descriptors do not affect prediction.

We compare four models that differ in how they use neighborhood information: HGT, untyped HGT (\uhgt), GAT, and a neighbor MLP (\mlp). % _________ Evaluation  _________________
\subsection{Performance Evaluation}
The benchmark systems exhibit imbalanced module distributions, with some modules containing many files while others contain only a few. Accuracy can therefore overstate performance by giving disproportionate weight to the largest modules. Therefore, we evaluate mapping performance using the F1 score, which balances precision and recall. Precision is the proportion of predicted module assignments that are correct, and recall is the proportion of true assignments that are recovered, and F1 is their harmonic mean, appropriate when module sizes are imbalanced.
 
We report F1 using both macro- and micro-averaging. Macro-F1 is computed independently for each architectural module and then averaged, giving equal weight to every module regardless of size. It is therefore sensitive to performance on small or underrepresented modules. Micro-F1 aggregates predictions across all files before computing F1, providing an overall measure that gives greater weight to larger modules. Reporting both metrics distinguishes class-balanced mapping performance from overall file-level performance.

\section{Results\label{sec:results}}
This section reports the results for semi-supervised code-to-architecture mapping across ten subject systems. RQ1 compares lexical, structural, and contextual file representations using a feature-only classifier. RQ2 examines how mapping performance changes when these representations initialize HGT with file, member, and folder context, and analyzes errors relative to directory-based predictions. RQ3 uses controlled experiments to examine how graph representation, training schedule, and neighbor processing affect the contribution of structural context. For RQ1 and RQ2, we report median macro- and micro-F1 scores over 100 runs per system and configuration; for RQ3, we report changes in F1 points between paired conditions over ten splits (Section~\ref{sec:controlled_setup}). Every test file is scored, regardless of prediction confidence.

Within each run or split, compared configurations use the same randomly sampled initial labeled set. For each system and metric, we use the two-sided Wilcoxon signed-rank test~\cite{wilcoxon}, pairing runs by their shared split. We apply Holm's correction within each comparison family, separately for macro-F1 and micro-F1, at $\alpha=0.05$. We report differences in median performance in F1 percentage points and, for RQ1 and RQ2, Cliff's $\delta$~\cite{cliff}, classified by magnitude as negligible (N, $|\delta|<0.147$), small (S, $0.147\leq|\delta|<0.33$), medium (M, $0.33\leq|\delta|<0.474$), or large (L, $|\delta|\geq0.474$).

\begin{GrayBox}{Answer to RQ2.}
Adding folder nodes improves macro-F1 and micro-F1 on all ten systems for all three representations, with significant large effects. File-level propagation and member nodes change scores less consistently, and member nodes also change feature construction. FFM largely matches the signal already available from the directory hierarchy, and on files where the directory baseline fails, adding folder nodes can replace correct FM predictions with incorrect FFM predictions. Strong folder-based scores therefore do not show that the model handles files for which directory location is insufficient or misleading.
\end{GrayBox}

\subsection{RQ3: Neighbor Information across Predictors and Input File Representations\label{sec:rq3}}
RQ2 shows that adding structure can raise or lower performance depending on the representation and system, and that file-level message passing lowered the median macro-F1 of N2V. RQ3 tests whether neighbor information improves mapping and whether its effect depends on the predictor, the input vector, or the training schedule. We first test whether N2V encodes graph structure beyond node degree, then compare four ways of using neighbors with N2V, repeat the comparison with the other input vectors, compare absolute scores, and test whether self-training explains the model-dependent pattern.

Differences are paired \emph{on} minus \emph{off} changes in F1 points, and positive values favor neighbor information. For N2V, we report the median of the three per-seed medians over ten splits, with their range as a sensitivity summary and not a confidence interval. For the other vectors, we report the median over the ten splits.

\parg{Do N2V vectors encode structure beyond node degree?} N2V vectors are learned from the dependency graph, so we first check whether they carry more than each file's degree, using the rewired-graph and shuffled-vector controls on Lucene, JabRef, and Bash. With neighbor information off, real vectors exceed rewired vectors by 56, 23, and 34 macro-F1 points, respectively, and shuffled vectors by 54, 21, and 34 points. Thus, the real vectors encode dependency structure beyond each file's degree. With rewired vectors, HGT improves macro-F1 by 8.2, 8.9, and 2.7 points, respectively. These controls use HGT only and cover three systems, so they do not show whether the same holds for other predictors or throughout the benchmark.

\parg{Is the N2V drop under message passing specific to HGT?} Figure~\ref{fig:rq3_n2v} shows the change in macro-F1 when neighbor information is switched on for each model with N2V vectors. Points left of zero indicate that neighbor information lowered performance. The comparison shows that the negative N2V result in RQ2 is specific to HGT rather than a general consequence of adding neighbor information to N2V.

GAT provides the clearest positive result. Under self-training, neighbor information raises macro-F1 on all ten systems by 1.2 to 5.1 points, with the same sign for every seed. Under supervised-only training, it raises macro-F1 on nine systems; Bash is the only exception, with a change of $-0.2$ points. GAT is never significantly lower than its off condition. The neighbor \mlp{} likewise improves macro-F1 on nine systems under both schedules, by 0.7 to 7.8 points under self-training. Five of these self-training gains are significant. HDC is the exception for the \mlp{}, decreasing by 0.9 points under supervised-only training and by 0.3 points under self-training, with the same sign for every seed.

HGT shows the opposite pattern. With self-training, neighbor information reduces macro-F1 on all ten systems by 1.1 to 10.1 points. Under supervised-only training, it reduces macro-F1 on nine systems, improving only on T.Mates by 8.6 points. The reductions are significant on six systems under each schedule. \uhgt{} largely mitigates these losses: under self-training, changes range from $-1.1$ to $+2.0$ points, with gains on six systems, although the direction varies across seeds on six systems. Only HGT and \uhgt{} show significant reductions relative to their off conditions. Thus, the effect of neighbor information with N2V depends on how the predictor incorporates it.

\parg{Does the pattern hold for other input representations?} Unlike N2V, file-level message passing raised median macro-F1 for W2V and \ft{} in RQ2, but the on/off comparison in Table~\ref{tab:rq3_reps} shows the same split between models. HGT lowers median macro-F1 under self-training with W2V ($-4.4$ points), \zs{} ($-1.7$), and \ft{} ($-2.5$). It improves on only two of ten systems with each vector and is significantly lower on eight systems with W2V and four with \ft{}, but on only one with \zs{}. GAT and the \mlp{} instead benefit from neighbor information with all three vectors and are never significantly lower than their off condition. GAT improves macro-F1 on eight systems with W2V and on nine with \zs{} and \ft{}, and the \mlp{} on all ten with W2V and \ft{} and on nine with \zs{}. \uhgt{} improves on seven systems with W2V, nine with \zs{}, and all ten with \ft{}. The gains of GAT and the \mlp{} are largest with \zs{} ($+6.9$ and $+7.7$ points). HDC, the exception for the \mlp{} with N2V, improves with W2V, \zs{}, and \ft{} by 4.7, 8.5, and 6.8 points, respectively.

The RQ2 and RQ3 results test different comparisons. In RQ2, F is compared with the graph-free MLP, which changes the predictor together with the available structure, and the later steps change the structure alone. RQ3 holds the predictor fixed and switches dependency neighbors on and off. A gain of F over the MLP in RQ2 can therefore come from the predictor and does not imply that HGT benefits when dependency neighbors are switched on.

\parg{Can self-training explain the model-dependent effect?} Neighbor effects retain their sign across the two schedules on most systems, with T.Mates under HGT as the main exception. Self-training therefore does not explain why neighbors help GAT and the \mlp{} but lower HGT. Self-training does, however, lower macro-F1 relative to supervised-only training at the same epoch budget: with N2V on all ten systems for HGT and on eight or nine for the other models, and with W2V and \ft{} in 66 of 80 system--model combinations. This loss is accompanied by a fall in median macro recall of 0.6 to 5.1 points across models and vectors, while micro-F1 changes by at most 1.5 points.


\begin{GrayBox}{Answer to RQ3.}
Dependency information improves mapping depending on how the predictor uses it. Neighbors improve GAT and the \mlp{} on most systems across all three representations, but HGT propagation usually lowers macro-F1. Using HGT on the untyped, undirected graph largely removes this loss, although direction and edge typing change together. GAT generally achieves the highest scores, and \ft{} is the strongest input overall. These patterns hold under both training schedules, so self-training does not explain the model-dependent neighbor effect.
\end{GrayBox}

\section{Discussion\label{sec:discussion}}

The research questions examine where architectural signal resides and how a mapping model can use it. RQ1 compares what file representations encode before message passing, RQ2 adds file, member, and folder context and compares the folder gains with a directory-based rule, and RQ3 examines how the way a predictor consumes dependency neighbors changes what they contribute. This section considers the three together and states the conditions under which they hold.

\parg{Dependency information in file representations.}
RQ1~\ref{sec:rq1} compares file representations before the predictor exchanges information between linked files, so the results reflect the architectural information encoded in each representation. Node2Vec, which is learned from the dependency graph alone, without labels, gives the highest micro-F1 on six of the nine systems and the highest macro-F1 on five. On Lucene, JabRef, and Bash, its vectors exceed those learned from a degree-preserving rewired graph by $56$, $23$, and $34$ macro-F1 points without message passing, so they encode dependency structure beyond node degree. Fine-tuned UniXcoder improves over its zero-shot counterpart on every system. Since the zero-shot encoder receives no dependency signal, this shows that fine-tuning on dependency-derived pairs adds information beyond that of pretrained code representations alone. Dependency information can therefore provide useful architectural signal before a predictor combines information across dependency links, either by encoding graph position directly in Node2Vec or by adapting a contextual code representation through dependency-guided fine-tuning.

The usefulness of this signal varies with the relation between dependency structure and the reference architecture. Node2Vec's micro-F1 is lower on the three least homophilic systems, SH-3D, HDF, and TeamMates (Table~\ref{tab:datasets}), with a median of $56$ compared with $74$ on the remaining six. When dependencies frequently cross module boundaries, random walks may place files from different modules in similar structural neighborhoods, limiting the module-discriminating information available to Node2Vec. Homophily is computed from the reference mapping and is therefore unavailable before a mapping exists; it is used here to interpret the observed pattern, not to select a representation in practice.

Fine-tuned UniXcoder shows a different pattern on the low-homophily systems. Its median micro-F1 is $67$ on SH-3D, HDF, and TeamMates, compared with $68$ on the remaining systems. It exceeds Node2Vec by $11$ micro-F1 points on SH-3D and TeamMates, which combine low homophily with the highest average degrees, $\langle k \rangle$ of $23.43$ and $22.90$. In these systems, dependency neighborhoods may span several modules, while the code content represented by UniXcoder can provide complementary evidence within such mixed neighborhoods. HDF is the exception: Node2Vec remains ahead of \ft{} ($55$ versus $47$ micro-F1), although every representation performs comparatively poorly on this system.

The two representations without dependency information, Word2Vec and zero-shot UniXcoder, show no consistent ordering. Their weaker overall results reinforce that the advantage of Node2Vec and \ft{} is associated with dependency information rather than with the use of a graph embedding or a code encoder alone.

The RQ2 and RQ3 comparison concerns a different use of dependencies. While Node2Vec learns file vectors from unlabeled random walks, the neighbor-based predictors use dependency links while learning the mapping from the available labels. The results show that useful dependency information in an input representation does not by itself establish that this additional neighbor use will help: directed, typed HGT propagation lowers F1 on most systems, whereas GAT and the neighbor \mlp{} generally gain. The effect therefore depends on how the predictor represents and processes the neighborhood information.

\parg{Folder organization and architectural exceptions.}
The gains from adding folder nodes in RQ2 show that directory organization helps reproduce the reference mapping. However, extending a directory assignment is different from identifying files that depart from it. The directory analysis separates these cases by checking which errors of a directory-based baseline the learned model repairs and which correct predictions it damages (Section~\ref{sec:directory_errors}).

Lucene and HDF mainly illustrate the first case. Their directories are pure under the reference mapping, and directory-baseline errors occur where the immediate directory has no labeled examples. Correcting these errors shows that a model can recover an assignment when local supervision is missing. It gives little evidence about conflicts between directory structure and architecture. Bash has mixed directories and therefore presents a different problem. JabRef shows why the distinction matters: adding folder context improves overall accuracy while losing more correct predictions on directory-baseline errors than it gains.

A mapping tool intended to identify architectural exceptions should therefore be evaluated on files that depart from their directory assignment, alongside overall accuracy. A rule-based directory baseline using only the initial labels provides a useful reference, but its repair and damage rates must be interpreted separately: repair is measured among baseline errors, whereas damage is measured among correct baseline predictions. Recovering assignments in directories without initial labels is useful, but does not establish that a model can identify files whose module assignment conflicts with their directory.

\parg{Dependency neighborhood processing and self-training.}
RQ3 distinguishes dependency information encoded in file representations from its additional use during prediction. GAT and \mlp{} generally benefit from dependency neighbors, whereas HGT often loses performance. Gains with N2V and \ft{} show that dependency-informed initialization does not make neighbor access redundant. However, GAT and HGT differ in graph direction, relation typing, and attention formulation, so the comparison does not isolate why GAT performs better. Removing direction and relation types from HGT reduces much of the loss, but changes both together. That neighbors improve GAT and \mlp{} with W2V and \ft{}, whose inputs carry no dependency information, reinforces the RQ1 finding that dependencies provide signal beyond file content. These findings concern the evaluated file-level predictors, not the usefulness of dependency types in general or the folder- and member-aware configurations.

On most systems, dependency neighbors help or hurt the predictor under both training schedules. Self-training therefore does not explain the general difference between predictors. TeamMates is an exception: HGT propagation improves macro-F1 under supervised-only training but lowers it under self-training. Equal training duration controls the epoch budget, but models can still acquire different pseudo-labels and follow different training paths.

A benefit from neighbors must also be distinguished from a benefit from self-training. On Chrome, \mlp{} benefits from neighbors under both schedules, yet self-training lowers its macro-F1. More broadly, self-training often lowers macro-F1 without a comparable change in micro-F1. Confident pseudo-labels may disproportionately reinforce large modules, but establishing this explanation requires examining which labels are added and how errors develop within each module.

\parg{Connectivity and neighbor information.}
Connectivity describes how much neighboring context is available, while homophily describes whether linked files share a module. Connectivity matters particularly for shallow message passing, whose reach is limited by the number of layers. Sparse neighborhoods restrict the features available for aggregation, whereas Node2Vec can encode more distant context through random walks. Connectivity can therefore constrain additional message passing even when the initial structural representation remains useful.

The N2V exceptions for GAT and \mlp{} occur on Bash and HDC, the systems with the lowest average degree. This is consistent with limited local context reducing the benefit of neighbor aggregation, but does not establish connectivity as the cause. In contrast, T.Mates and SH-3D have low homophily but among the highest average degrees, and they are the systems where file-level message passing significantly raised N2V micro-F1 in RQ2. HDF has similarly low homophily but a much lower degree and no comparable gain. These observations suggest that connectivity is relevant to the context available for shallow message passing, but with nine systems and correlated descriptors we cannot separate connectivity from homophily, system size, or label scarcity, and we did not test this.

\parg{Implications for evaluating mapping models.}
Evaluation should establish what the input representation already provides, then isolate neighbor access within a fixed predictor and training schedule. Comparing a graph model with a graph-free MLP changes both the predictor and its access to structure; switching neighbors on and off within the same predictor tests whether that access helps.

Macro and micro F1 scores should be read together, since correctly mapping more files does not necessarily improve performance across modules. The directory analysis adds a further requirement: aggregate scores should be accompanied by evidence about files that depart from directory-based assignments. Together, these comparisons distinguish the contributions of input features, neighbor processing, and training schedule, while exposing limitations hidden by aggregate scores.These points concern the nine systems and the compared configurations and do not rank the signals or the predictors in general.

\section{Threats to Validity\label{sec:threats}}

\parg{External validity:} The benchmark contains nine open-source systems in Java, C, and C++, each with one reference decomposition, so the results describe these systems and their reference architectures. All systems had been inspected before the full experiment, and the comparisons were not fixed in advance. The rewiring control, on which the claim that Node2Vec encodes structure beyond node degree rests, covers three systems. Relationships between performance and structural properties are reported as associations, not causal effects, since the benchmark does not allow these properties to be separated from one another or from system size and label availability. Whether the findings extend to other systems, alternative reference decompositions, or the evolution of a mapping over time was not tested.

\parg{Internal validity:} Dependencies are extracted using static analysis, which can miss dependencies that arise only at runtime, for example through reflection, function pointers, conditional compilation, or macro expansion, and can introduce imprecise edges when references cannot be resolved unambiguously. Because the predictors that use neighbors depend on the extracted graph, missing and incorrect edges can affect their predictions. Models with neighbor information on and off are trained separately, so their differences also include differences in learned weights and, under self-training, in pseudo-label histories.

The analyzed source code may not match the version a published mapping describes. Several benchmark mappings were created years before the source versions used here were obtained, and the files included in a system can depend on its build configuration, so the analyzed file set may differ from the one the mapping covers. In older systems, architectural drift may also weaken the correspondence between a file and its assigned module.

Files can plausibly belong to more than one module, and annotators may assign them differently. Because the initial labeled set is sampled from the same mapping used for evaluation, an incorrect assignment can both mislead the model during training and penalize an architecturally plausible prediction.

\parg{Statistical validity:} Repeated splits contain overlapping files, and runs from the same system are not independent system replications, so we report effects per system and do not treat the runs as independent datasets. With 100 runs per configuration, statistical tests may identify small systematic differences that are not practically meaningful, so we report effect sizes alongside significance. These runs capture variation from different initial labeled sets, but not from stochastic model training. The seeds governing model initialization and training were not retained, so an independent rerun would use different training seeds even with the same labeled sets, and the effect of this variation on borderline outcomes was not assessed. The RQ3 experiments record their seeds, but ten splits and three embedding seeds for Node2vec do not cover every source of stochastic variation.

\parg{Construct validity:} Scores measure agreement with a particular reference architecture. Folder layout may reflect the same developer decisions or reconstruction evidence used to define that architecture. Strong directory prediction therefore does not establish independent recovery of architectural intent. Directory purity and neighbor-label conflict use complete reference labels only for retrospective analysis. Training and prediction use the initial labeled set and model-generated pseudo-labels, not true test labels.

Every test file is scored regardless of confidence. In this single-label task, micro-F1 equals accuracy; macro-F1 gives equal weight to modules represented in the test truth. A module whose only file is anchored in training can be absent from that split's macro average. Repair and damage rates have different denominators, and repair is undefined when the directory baseline makes no errors. File/split event counts may include the same file repeatedly. A file spanning several concerns is still forced into a single reference module.

The study is transductive: representation learning and graph processing can use unlabeled test nodes and their edges. It does not establish performance on newly arriving files outside the observed graph. Other information sources, including change history and dynamic dependencies, are outside the evaluated scope.

\section{Conclusion\label{sec:conclusion}}

This study examines which implementation-level signals, including code text, static dependencies, folder organization, and member-level information, carry architectural information and how their representation and use affect code-to-architecture mapping on ten systems. We encode file information using lexical Word2Vec, structural Node2Vec, and contextual UniXcoder in zero-shot (\zs{}) and dependency-guided fine-tuned (\ft{}) variants, and evaluate these representations with MLP- and GNN-based predictors. Representations that encode dependencies, Node2Vec and \ft{}, outperform Word2Vec on most systems when evaluated with the MLP, whereas Word2Vec and \zs{}, which do not, perform comparably. Dependency-guided fine-tuning significantly improves mapping performance over \zs{} on most systems, although no representation is best on every system. Folder nodes produce the largest and most consistent gains within HGT variants, but largely recover information already available to a directory rule using the initial labels and do not consistently improve the files on which that rule fails. Member-node gains are less uniform and cannot generally be separated from changes in feature construction and placement.

The controlled experiments distinguish dependency information encoded in file representations from its additional use during prediction by keeping the input vectors fixed and switching direct dependency neighbors on and off for four predictors, under both training schedules and on all ten systems. Access to direct dependency neighbors improves performance across the evaluated representations for both GAT, which uses message passing, and the neighbor \mlp{}, which concatenates own-file features with mean-neighbor features, with larger gains for Word2Vec and \zs{} than for Node2Vec. These results show that dependency links provide useful information beyond lexical and pretrained code features, while gains with Node2Vec and \ft{} show that neighbor access can also complement representations that already encode dependencies. Whether neighborhood information helps depends on how it is processed: with Node2Vec vectors, GAT and \mlp{} improve macro-F1 on at least nine of ten systems under both schedules, whereas HGT lowers it on at least nine. Message passing over the directed, multi-relational dependency graph in HGT therefore benefits less than the simpler GAT and neighbor \mlp{}, and its median macro-F1 change is also negative with the other vectors. Removing direction and edge types from HGT removes most of this loss, but the two are changed together, so the experiments do not show which of the two accounts for it.

Dependencies carry architectural signal beyond file content, and a mapping model can use it in two ways: by encoding it in the file representation, as Node2Vec and dependency-guided fine-tuning do, or by giving the predictor access to direct neighbors. Both help, but the second depends on how the neighbors are processed. Evaluating a mapping model should therefore establish what its input already encodes, isolate neighbor access within a fixed predictor, and examine the files that depart from their directory assignment. These findings concern ten systems and the compared configurations, and do not rank the signals or the predictors in general.
