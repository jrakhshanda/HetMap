Title-- What Carries Architectural Signal? A Code-to-Architecture Mapping Study

Abstract-- Assigning source files to reference architecture modules supports conformance checking and system understanding. Code text, static dependencies, folder organization, and member-level information can inform this mapping, but their contributions depend on how they are represented and used. We investigate these contributions on ten Java, C, and C++ systems with limited labeled data. We compare lexical, structural, and contextual file representations using a multilayer perceptron (MLP), a Graph Attention Network (GAT), and a Heterogeneous Graph Transformer (HGT). With HGT, we vary graph granularity from source files alone to files with their members and enclosing folders. We also control access to dependency-neighbor information within fixed predictors and compare aggregation in one or both directions.

Representations that encode dependencies provide strong baselines when evaluated with the MLP. Additional neighbor information can improve mapping, but its benefit depends on the predictor and aggregation direction; under aggregation in both directions, the GAT achieves the highest median macro-F1 with every representation. Within HGT variants, folder nodes produce the largest and most consistent gains, while member nodes provide no consistent improvement. However, a directory rule using the same labeled files reaches similar accuracy on most systems, and folder gains do not consistently extend to files the rule assigns incorrectly. Evaluation should therefore distinguish the contribution of additional graph context from information already available in file representations and directory organization.

\section{Introduction\label{sec:intro}}

Maintaining a software architecture requires knowing which implementation elements belong to its modules. That correspondence can become difficult to maintain as a system grows: new files introduce responsibilities and dependencies, while architectural documentation may lag behind the implementation. Code-to-architecture (C2A) mapping addresses this problem by assigning source files to the modules of a reference architecture. The resulting mapping supports reflexion modeling, which compares implementation dependencies with architectural relations to identify divergence~\cite{reflexion1}. It therefore connects the modular decomposition used to reason about a system~\cite{parnas1972,clements2003} to the code in which that decomposition is realized.

Several sources of evidence can support a mapping. Identifiers express domain concepts and implementation roles. Contextual code representations capture information from declarations and operations. Static dependencies locate a file among other files with which it interacts, while directories record how developers organize the project~\cite{sarif,negar,garcia2013}. These sources need not agree: a utility may depend on several modules, terminology may be shared across responsibilities, and a directory may contain files assigned to different architectural modules.

The usefulness of an information source also depends on how it enters a predictor. A dependency embedding can encode graph structure before a classifier sees a file. Propagating over dependencies then supplies a second form of access to related files, with its own assumptions about direction, relation types, and aggregation. A gain from the embedding does not establish that this additional propagation will help. Similarly, agreement with a reference architecture may partly reflect agreement between that architecture and the directory structure, in which case aggregate scores do not show how a folder-aware model handles files whose directory is not indicative of their module. These distinctions motivate studying both the information supplied to a model and the changes caused by the way it processes that information.

Prior graph-based representation learning work on architecture recovery represents these sources in different ways, from Node2Vec random walks on the dependency graph~\cite{negar} and graph attention with diffusion-based rewiring~\cite{structsar} to a graph autoencoder over identifier and folder tokens~\cite{gaer}. For mapping, prior work combines lexical and organizational features with dependencies in a single graph neural network~\cite{jabeen2025graph,c2a_mapping}. Because all signals enter that model together, and the predictors compared there differ in neighbor access as well as in architecture, it remains unclear how much each signal contributes and how it should be represented.

We examine this question through C2A mapping, formulated as a classification problem in which each file is assigned to one module of the reference architecture. We work in a transductive low-label setting, where a small sample of files covering every module is already mapped, and the model infers the remaining assignments. The model is trained on the labeled files alone. This setting allows us to examine how file representations and graph relations contribute under limited supervision.

Our evaluation uses ten Java, C, and C++ systems and covers lexical Word2Vec, structural Node2Vec, and contextual UniXcoder representations. These serve as inputs to an MLP, to a Heterogeneous Graph Transformer (HGT)~\cite{hgt}, and, in the dependency comparison, to a neighbor MLP and a Graph Attention Network (GAT)~\cite{gat}. The heterogeneous configurations contain file nodes and, where applicable, folder nodes and one aggregate member node per file. They vary both the context available to a file and where feature content is stored. The representations themselves differ in training, vector size, and source content, so their comparison is between representation pipelines and not between isolated information sources.

\noindent The study is guided by three research questions:
\begin{itemize}[leftmargin=1em, itemsep=1pt]
    \item \textbf{RQ1.} How does mapping performance vary across lexical, structural and contextual file representations?
    \item \textbf{RQ2.} How does adding member and folder nodes to file-level HGT change mapping performance, and how do folder-aware predictions compare with a directory rule?
    \item \textbf{RQ3.} How does using dependency neighbors change mapping performance, and how do the predictor and aggregation direction affect this change?
\end{itemize}
 
This study contributes an evaluation of C2A mapping that separates the information supplied to a model from the way the model uses it. Each research question varies one component while everything else, including the labeled splits and training settings, is held fixed: the file representation, the graph context available to HGT, and access to dependency neighbors within a fixed predictor. We also compare folder-aware models with a directory rule that uses the same labeled files and examine the files the rule assigns incorrectly, since aggregate scores alone do not show whether a gain exceeds what directory organization already provides. Code and data are available on GitHub\footnote{\label{fn:code}\url{https://github.com/sse-lnu/hetmap}}.

\section{Background \label{sec:background}}

Software artifacts are naturally relational and multi-typed. A system contains folders, source files or classes, and finer-grained program elements such as methods and fields, connected through relations that include folder containment, file-to-member composition, and static code-level dependencies.

To preserve these distinctions, we represent each software system as a typed graph:
$$G=(V, E,\mathcal{A},\mathcal{R}),$$
where $V$ and $E$ are the sets of artifact nodes and relations between them, respectively. The mappings $\tau: V \rightarrow \mathcal{A}$ and $\phi: E \rightarrow \mathcal{R}$ assign node and relation types. In our most detailed configuration, $\mathcal{A}$ contains folder, file, and aggregate member types, while $\mathcal{R}$ distinguishes folder containment, file-to-member composition, and a single dependency relation that merges all file-level static dependencies. The file-level graph is homogeneous, and adding folder or member nodes makes it heterogeneous.

A relation's meaning depends on its type and the types of its source and target nodes in $G$. We describe an edge $e_{s,t}$ from node $s$ to node $t$ by the meta-relation $\langle \tau(s), \phi(e_{s,t}), \tau(t) \rangle$. For example, $\langle \text{folder}, \text{contains}, \text{file} \rangle$ captures project organization, whereas $\langle \text{file}, \text{depends on}, \text{file} \rangle$ captures code-level coupling. These meta-relations preserve the distinction between structural organization and implementation dependencies, which a homogeneous graph with one node type and one relation type does not explicitly represent.

HGT~\cite{hgt} exploits such meta-relations during message passing by conditioning attention and message transformation on the source node type, edge type, and target node type. GAT~\cite{gat} also uses attention-based message passing, but its standard formulation does not explicitly distinguish node or relation types. HGT can also operate on a graph with a single node type and a single relation type, although this does not make its attention mechanism equivalent to that of GAT.

The initial node features determine what information is available before message passing, while graph structure determines which nodes exchange information. Depending on how they are encoded, a file's features can capture lexical evidence from its identifiers, structural evidence from its position in the dependency graph, or contextual evidence from its code.

A lexical embedding trained on identifier tokens captures naming patterns but does not explicitly encode dependency structure or implementation syntax and behavior. A graph embedding such as Node2Vec~\cite{node2vec} instead encodes structural neighborhoods without using code content. Such embeddings have been used to capture dependency-based cohesion in architecture recovery~\cite{negar,structsar}.

Contextual representations from pretrained code encoders such as UniXcoder~\cite{unixcoder} capture the syntactic and behavioral content of an implementation that lexical features miss, but their pretraining objectives do not target architectural grouping: files with similar code can belong to different modules. Contrastive learning adapts an encoder to a chosen notion of similarity by bringing designated positive pairs closer than other in-batch examples treated as negatives, using an InfoNCE objective~\cite{infonce}. Dependency-derived positive pairs encourage embeddings to reflect dependency proximity, which need not align with reference-module membership.

\section{Methodology\label{sec:method}}

This section presents the methodology for studying how architectural signals and graph design choices affect C2A mapping. We first formulate the mapping task and then describe the graphs and the structural, lexical, and contextual features used to initialize their nodes. We then present the MLP, HGT, and GAT predictors.
 
Each research question varies one of these components and holds the others fixed. RQ1 varies the file representation, using the MLP. RQ2 varies the graph variant for each representation, using HGT because it handles the node and relation types of the heterogeneous variants. RQ3 varies the predictor, comparing the neighbor MLP with GAT and HGT, and the dependency neighbors they receive.

\subsection{Problem Formulation\label{sec:problem}}
We formulate the mapping task as node classification over a software graph $G=(V, E,\mathcal{A},\mathcal{R})$, where $\mathcal{A}$ and $\mathcal{R}$ denote the sets of node and relation types. Let $V_f \subseteq V$ be the set of file nodes, which are the targets of the mapping task. A small subset $L \subset V_f$ is labeled with known architectural module assignments $Y_L$, and the remaining file nodes $U = V_f \setminus L$ are unlabeled. The task is to learn a model:
\begin{equation}
    f_{\theta}: (G, L, Y_L) \rightarrow \hat{Y}_U,
\end{equation}
where $\theta$ denotes the learnable parameters. The model is trained on the labeled files only, but all nodes of $G$, labeled and unlabeled, are part of the graph during training.
 
Each model computes a $d$-dimensional embedding $z_i$ for every file $i \in V_f$, and the architectural module of a file is predicted from this embedding.

\subsection{Graph Construction\label{sec:het_graph}\label{sec:graph_variants}}
We represent the software system as a graph of software artifacts connected by folder organization, member containment, and static dependencies.

To study the individual and combined contributions of folder and member information, we construct four graph variants that differ in the node types they contain. They are named after these types: F (file nodes only), FF (folder and file nodes), FM (file and member nodes), and FFM (folder, file, and member nodes). All variants retain the dependency relation. F is homogeneous, with one node type and one relation type, and the other three variants are heterogeneous. Figure~\ref{fig:graph_variants_overview} provides a visual overview.

\subsubsection{Nodes and Relations}
The complete graph (FFM) has three node types. File nodes represent source files and are the targets of C2A mapping. Because logical components are often implemented through namespaces or directory structures that group source code providing a particular functionality~\cite{fundamentals_sa, garcia2013}, folder nodes represent directory levels of the project, with one node per level. Each file has one summarized member node covering the methods, fields, constructors, and variables of that file. This retains member-level information while avoiding the large and sparse graphs produced by representing individual members.

Four relations connect these nodes, as listed in Table~\ref{tab:relation_types}. Three are structural and encode organization and containment, and the fourth encodes static dependencies. Folder nodes are connected through \emph{parent\_of} edges, forming chains such as \texttt{app} $\rightarrow$ \texttt{app/ui} $\rightarrow$ \texttt{app/ui/views}, and \emph{contains} edges link each folder to its files. A \emph{belongs\_to} edge links each member node to its enclosing file.

Messages along structural relations flow toward the file. Folder information passes down the hierarchy through \emph{parent\_of} and \emph{contains} edges, and member information passes up to the file through \emph{belongs\_to} edges. No reverse edges are added, so folder and member nodes are not updated from files through structural relations.

The fourth relation, \emph{depends\_on}, encodes static dependencies, which provide direct evidence of how source files interact~\cite{negar, deps_impact}. Dependencies were extracted with the Depends tool~\cite{depends}, which analyzes the syntactic structure of the projects and identifies entities together with several categories of static relations. We merge all dependency types into a single relation, drop duplicate edges, and remove edges whose endpoints belong to the same file.

Dependency endpoints depend on the graph variant. In FM and FFM, dependencies connect either two files or two member nodes. Dependencies between a file and a member are resolved between their corresponding files. In F and FF, all member endpoints are replaced by their enclosing files, so all dependencies connect file nodes.

RQ1 uses no graph structure, and RQ3 uses the homogeneous file-level graph F. RQ2 uses all four variants to examine progressively richer graph structure, adding folder nodes in FF, member nodes in FM, and both in FFM.

\subsection{Node Feature Initialization \label{sec:node_features}}
Folder nodes are initialized in the same way in every setting. File and member nodes are initialized with one of the representations compared in RQ1: lexical embeddings from Word2Vec, structural embeddings from Node2Vec, or contextual embeddings from UniXcoder, used zero-shot or fine-tuned with dependencies.

Member information enters the model differently across representations. Word2Vec includes member identifiers in file vectors when member nodes are absent and places them in member nodes otherwise. UniXcoder provides member text only through member nodes, while Node2Vec assigns each member node its file's vector. Adding member nodes thus changes the placement or availability of information as well as the graph structure, so comparisons across graph variants are interpreted separately for each representation.

\subsubsection{Folder Node Features}
Folder nodes use a binary bag-of-words representation of the folder tokens along their paths, after removing common project-root tokens. For example, \texttt{app/ui/views} is represented by \texttt{app}, \texttt{ui}, and \texttt{views}. Including the tokens of its ancestors preserves each folder's hierarchical context.

\subsubsection{Word2Vec (W2V): Lexical Features\label{sec:node_w2v}}
Source code identifiers encode domain concepts and implementation roles, making them useful signals for C2A mapping~\cite{sarif}. Following Jabeen et al.~\citep{gaer}, we extract tokens from file names and from the identifiers of members, namely methods, fields, constructors, and variables. We split camelCase, PascalCase, and snake\_case identifiers, convert tokens to lowercase, and remove stopwords and non-alphabetic tokens. Each node vector is the mean of the skip-gram Word2Vec embeddings of its associated tokens~\cite{word2vec}.

In FM and FFM, file nodes use file-name tokens, while member nodes use member identifiers. In F and FF, member identifiers are included in the file vector instead, and the MLP uses this same file vector. Member identifiers therefore remain available in every variant.

\subsubsection{Node2Vec (N2V): Structural Features \label{sec:node_n2v}}
Chen et al.~\citep{negar} observe that files in the same architectural module can occupy a dense local dependency region without being directly connected. They use random-walk embeddings to capture this longer-range structure for architecture recovery. In our earlier study of dependency-only recovery, which follows their setup, Node2Vec was among the best-performing learned representations~\cite{structsar}. Therefore, we use Node2Vec~\cite{node2vec} embeddings computed with uniform random walks on the undirected file-level dependency graph as a structural initialization. These embeddings encode dependency structure without using identifiers or folder location.

In FM and FFM, each summarized member node receives the Node2Vec embedding of its corresponding file.
 
\subsubsection{UniXcoder: Contextual Features \label{sec:unixcoder}}
For contextual initialization, we use UniXcoder~\cite{unixcoder}, a pretrained code transformer. We parse each source file with Tree-sitter~\cite{tree_sitter} using the corresponding Java, C, or C++ grammar. The syntax tree determines which source fragments are passed to the encoder, but is not itself an input to the model. Extraction produces two views. The file-level view contains type declarations, fields or global variables, and constructor signatures with short body excerpts where applicable. The member-level view contains methods or functions. Each view produces one vector per file. Member-level text is split into overlapping chunks whose embeddings are mean-pooled.
 
The zero-shot variant (\zs{}) uses the pretrained weights. The dependency-guided variant (\ft{}) is fine-tuned separately for each system with a contrastive objective~\cite{infonce} using dependency-based positive pairs. Fine-tuning uses only the file-level views, and module labels do not enter the loss. The fine-tuned encoder then encodes both views and produces one vector per view for each file, so member-level text is encoded but is not part of the fine-tuning objective.
 
Positive pairs are drawn from the two-hop neighborhood to capture longer-range dependency structure~\cite{structsar}, with dependencies treated as undirected. For each anchor file, two positives are sampled at random from the eight two-hop candidates that share the most one-hop neighbors with it. Files without a two-hop candidate fall back to a direct neighbor. Other files in the batch serve as negatives, except directly connected files, which are masked unless selected as the positive pair.

\subsection{Mapping Models\label{sec:mapping_models}}
We compare models that use file features alone with models that incorporate graph structure. RQ1 uses the MLP, RQ2 uses HGT, and RQ3 compares the neighbor MLP, GAT, and HGT. All models use the same classification head to predict architectural modules. Throughout, $\mathcal{N}(\cdot)$ denotes the neighborhood of a node.

\subsubsection{Multilayer Perceptron (MLP)\label{sec:mlp}}
The MLP predicts module logits directly from a file-level input vector. Each hidden layer computes:
\begin{equation}
h_i^{(k+1)} = \text{ReLU}\big(W^{(k)} h_i^{(k)} + b^{(k)}\big),
\end{equation}
with $h_i^{(0)} = x_i$ the file feature vector and $W^{(k)}, b^{(k)}$ the learnable parameters of layer $k$, and ReLU is the rectified linear unit~\cite{relu}. The input $x_i$ contains the single representation being evaluated.
 
For RQ3, we incorporate dependency neighborhood information in the MLP by concatenating each file's vector $x_i$ with the mean $\bar{x}_{\mathcal{N}(i)}$ of its direct neighbors' vectors in the dependency graph, giving $[x_i \,\|\, \bar{x}_{\mathcal{N}(i)}]$. We refer to the MLP with this input as the neighbor MLP (\mlp{}). With neighbors disabled, the input is $x_i$ alone, as in RQ1, so enabling neighbors also doubles the input width of the first layer.
 
\subsubsection{Heterogeneous Graph Transformer (HGT)\label{sec:hgt_model}}
Node types have different feature spaces depending on the graph variant and initialization strategy. So HGT first maps the input vector $x_t$ of each node $t$ into a shared hidden space using a type-specific linear transformation followed by ReLU, which gives its initial representation $h_t^{(0)}$. One HGT layer~\cite{hgt} then updates node representations through multi-head attention over their neighbors.
 
For a target node $t$ and a source node $s$ connected by an edge $e$, the layer computes a message $M(s,e,t)$ and an attention weight $\alpha(s,e,t)$, and aggregates them as:
\begin{align}
m_t &= \sum_{s \in \mathcal{N}(t)}
       \alpha(s,e,t)\, M(s,e,t), \\
M(s,e,t) &= W^{\mathrm{MSG}}_{\phi(e)}\,
            V_{\tau(s)}\, h_s, \notag
\end{align}
\begingroup
\fontsize{9.5pt}{12pt}\selectfont
\begin{equation*}
\alpha(s,e,t)
= \operatorname*{softmax}_{s \in \mathcal{N}(t)}
\frac{
  \big(K_{\tau(s)} h_s\big)^{\top}
  W^{\mathrm{ATT}}_{\phi(e)}\,
  \big(Q_{\tau(t)} h_t\big)\,
  \mu_{\langle \tau(s),\phi(e),\tau(t)\rangle}
}{\sqrt{d_h}}.
\end{equation*}
\endgroup

\noindent where $\tau(\cdot)$ is the node type, $\phi(e)$ is the edge type, $V$, $K$, and $Q$ are type-specific linear transformations, $W^{\mathrm{MSG}}$ and $W^{\mathrm{ATT}}$ are edge-type-specific matrices, $\mu$ is a learned prior for each meta-relation, $d_h$ is the head dimension, and attention-head indices are omitted for brevity. These parameters allow a \emph{contains} edge from a folder and a \emph{depends\_on} edge from a dependent file to receive different attention weights.

After combining the attention-head outputs, we denote the resulting message by $m_t$. In our implementation, this message is combined with the node's projected input $h_t^{(0)}$ through a residual connection~\cite{residual_connection} followed by layer normalization:
\begin{equation}
h_t^{(1)} = \mathrm{LayerNorm}\left(m_t + h_t^{(0)}\right).
\end{equation}
Folder and member nodes, when present, contribute to file representations through message passing. 
 
\subsubsection{Graph Attention Network (GAT)\label{sec:gat_model}}
GAT~\cite{gat} aggregates neighbor representations using attention parameters shared across neighbors within each head, without the node-type- or edge-type-specific parameters of HGT. The outputs of the attention heads are concatenated. Our GAT implementation uses the same input projection, residual connection, and layer normalization as HGT, while replacing its neighbor aggregation mechanism. We add no self-loops; the residual connection retains the node's own representation.
 
\subsubsection{Classification Head\label{sec:head}}
All three predictors use the same classification head. The file embedding $z_i \in \mathbb{R}^{d}$, obtained from the last hidden layer of the MLP or the message-passing layer of GAT and HGT, is passed to a linear layer that produces one score per architectural module. A softmax converts these scores into a probability distribution:
\begin{equation}
\label{eq:head}
\begin{aligned}
p_i &= \text{softmax}\big(W_c z_i + b_c\big), \\
\hat{y}_i &= \arg\max_m p_{i,m},
\end{aligned}
\end{equation}
where $W_c \in \mathbb{R}^{|M| \times d}$, $b_c \in \mathbb{R}^{|M|}$, and $|M|$ is the number of architectural modules. The predicted module $\hat{y}_i$ is the one with the highest probability. Training minimizes categorical cross-entropy over the labeled file nodes.

\subsection{Experimental Configurations}
We repeat each experiment 100 times, each with a different initial labeled set. In each run, we randomly sample 5\% of the file nodes, with a minimum of 30 and a maximum of 200 files, and add one file from each GT module not represented in the sample. We use the same 100 initial labeled sets across all experiments and configurations, which allows paired comparisons. This procedure imposes a bounded labeling budget rather than a constant labeled proportion: before the module-coverage additions, the random sample covers approximately 9--20\% of the files in the five systems subject to the floor (C.Img, SH-3D, Bash, HDF, and HDC) and approximately 1\% in Chromium, the only system subject to the cap.

\parg{Input representations.}
For each system, Word2Vec embeddings are 128-dimensional vectors trained for 20 epochs with a context window of five on the file names and identifiers.

Node2Vec learns 128-dimensional vectors from uniform random walks ($p=q=1$) on the undirected file-level dependency graph, with walk length 30, 200 walks per file, window 15, five skip-gram epochs, and five negative samples. Chromium uses 100 walks per file and one negative sample.
 
For \ft{}, UniXcoder is fine-tuned separately for each system with an InfoNCE temperature of $0.05$, AdamW with a learning rate of $2\times10^{-5}$, a batch size of eight, and two epochs with a fixed seed. Only the upper four of the twelve encoder layers are updated, while the token embeddings and the lower eight layers stay frozen. Both UniXcoder variants encode file inputs with a 512-token limit and member inputs in overlapping 256-token windows with a stride of 128, mean-pooled before normalization, producing 768-dimensional features.
 
All input representations are generated once per system and reused in every run and experiment.

\parg{Training models.}
All models are trained with Adam at a learning rate of $0.001$ for 200 epochs. The MLP has two hidden layers of 256 dimensions, and GAT and HGT use one layer with 256 hidden dimensions and four attention heads.

\parg{Controlled comparisons.}
RQ1 trains the MLP on each of the four representations, which isolates the information in the file representation because the MLP uses no graph structure.

RQ2 trains HGT on all graph variants (Figure~\ref{fig:graph_variants_overview}) with Word2Vec, Node2Vec, and \ft{} features, using directed dependency edges. We additionally train all four HGT variants with two layers to test whether one layer limits what a file receives from its neighbors. We also train \textbf{FD}, an HGT model on graph F whose \ft{} file vector is extended with a binary folder-path vector, including ancestor folders. This vector uses the same tokenizer and vocabulary as the folder-node features (Section~\ref{sec:node_features}), with one dimension per distinct folder token in the system. FD provides folder information without folder nodes.

RQ3 consists of controlled comparisons on the file graph, with all four representations. Within each predictor (MLP, GAT, and HGT), we vary only whether dependency neighbors are available and in which direction information flows. We keep the file representations, initial labeled sets, and training settings fixed and compare three settings. With neighbors \emph{disabled}, each file uses only its own representation. With \emph{directed} aggregation, a dependency edge from file $u$ to file $v$, where $u$ depends on $v$, carries information from $u$ to $v$. Each file therefore receives information from the files that depend on it. With \emph{undirected} aggregation, we also add the reverse edge, allowing each file to receive information from files it depends on. For the MLP, these settings determine which files contribute to the neighbor vector; for GAT and HGT, they determine which files send messages.

The MLP with neighbors disabled is the RQ1 classifier, and HGT with directed neighbors on the file graph is the F configuration of RQ2, so these runs are shared. In total, the experiments comprise 58,000 runs.

% _______________ Directory Reference Predictor ________________
\subsubsection{Directory Hierarchy Baseline\label{sec:dir_predictor}}
To assess how much folder-based configurations exploit files in the same directory sharing a module, we use a rule-based predictor based on the directory hierarchy and the initial labeled files. For each unlabeled file, it assigns the most common module among labeled files in the same directory. If none are present, it searches the directory subtree and then the subtrees of its parent directories until it finds labeled files. Ties are resolved by the module's frequency in the complete initial labeled set and then alphabetically. If no labeled files are found, the predictor assigns the most common module in the complete initial labeled set. It uses the directory hierarchy, but not directory-name text, source code, embeddings, dependencies, or test labels.
 
We apply the predictor to all 100 initial labeled sets and compare it with HGT using \ft{} features on the directed FM and FFM graphs and with FD. For each system, we report the accuracy of the predictor, FM, FFM, and FD, which equals micro-F1 because each file has exactly one module label. For the files that the predictor assigns incorrectly, we also report the accuracy of each compared model on those files.

% _________ Evaluation _________________
\subsection{Performance Evaluation}
The benchmark systems have imbalanced module sizes, so overall accuracy can hide poor performance on smaller modules. We therefore report both macro-F1 and micro-F1. F1 is the harmonic mean of precision and recall, which measure the correctness of predicted assignments and the coverage of true assignments, respectively. Macro-F1 averages the F1 scores of individual modules, giving each module equal weight regardless of size. Micro-F1 aggregates predictions across modules, giving each file equal weight. Reporting both captures performance across modules as well as overall file-level performance.

Because compared configurations use the same initial labeled sets, we pair runs by split. We use the two-sided Wilcoxon signed-rank test~\cite{wilcoxon}, a non-parametric test, to compare configurations separately for each system and metric without assuming normally distributed score differences. We apply Holm's correction across the ten systems for each metric and pair of compared configurations, using a significance level of $\alpha=0.05$. 

To quantify the magnitude of the differences, we also compute Cliff's $\delta$~\cite{cliff} from the two sets of 100 scores. We classify its magnitude as negligible (N, $|\delta|<0.147$), small (S, $0.147\leq|\delta|<0.33$), medium (M, $0.33\leq|\delta|<0.474$), or large (L, $|\delta|\geq0.474$)~\cite{romano2006}.

\section{Results\label{sec:results}}
This section reports the results for code-to-architecture mapping across ten subject systems. RQ1 compares lexical, structural, and contextual file representations using an MLP. RQ2 examines how mapping performance changes when Word2Vec, Node2Vec, and \ft{} initialize HGT with file, member, and folder context, and analyzes errors relative to directory-based predictions. For RQ3, we report the median of the paired differences between conditions over the 100 splits. Summary tables give the median of these per-system values across the ten systems. F1 is computed only on the held-out test files of each split.

\section{Discussion\label{sec:discussion}}
The research questions examine where architectural signal resides and how a mapping model can use it. RQ1 compares file representations before message passing, RQ2 examines file, member, and folder context and compares the folder gains with a directory-based rule, and RQ3 examines how predictor choice and aggregation direction affect the contribution of dependency neighbors. This section discusses these findings together.

\subsubsection*{Dependency Information in File Representations}
Dependency information can support mapping before message passing, through the graph position encoded by Node2Vec or through dependency-guided adaptation of a code encoder. The advantage of these representations over Word2Vec, and of fine-tuned UniXcoder over its zero-shot counterpart, suggests that dependency information is useful beyond what the evaluated lexical and pretrained code representations provide. The representations also differ in training, vector size, and source content, so these comparisons are between representation pipelines and not between isolated information sources.

The usefulness of this signal varies with the relation between dependency structure and the reference architecture. Node2Vec’s micro-F1 is lower on the three least homophilic systems, SH-3D, HDF, and T.Mates (Table~\ref{tab:datasets}), with a median of $58$ compared with $72$ on the remaining seven. Node2Vec learns dependency proximity from files that co-occur on random walks, without using the GT mapping. When dependencies frequently cross module boundaries, files from different modules may co-occur on walks and receive similar vectors, making the modules harder to distinguish.

The advantage of fine-tuned UniXcoder over Node2Vec on SH-3D and T.Mates suggests that code content may provide complementary evidence in these mixed neighborhoods. HDF does not follow this pattern, so low homophily alone does not explain their relative performance; HDF is also the smallest system, and every representation performs comparatively poorly on it. Homophily is used here to interpret the observed pattern, not to select a representation, since computing it requires the reference mapping.
 
Encoding dependencies in the initial representation and aggregating dependency neighbors during mapping are two uses of the same information source, and the second does not necessarily replace the first. Word2Vec and zero-shot UniXcoder gain more from neighbors than Node2Vec and fine-tuned UniXcoder do, yet fine-tuned UniXcoder still has the highest median macro-F1 for every predictor. Conversely, useful dependency information in a representation does not guarantee a benefit from further aggregation: RQ3 shows that this benefit depends on both aggregation direction and predictor choice.

\subsubsection*{Folder Organization and Architectural Exceptions}
The gains from adding folder nodes in RQ2 show that directory organization helps reproduce the reference mapping. They do not show that this information must reach a file through message passing over folder nodes, since supplying the same information directly in the file vector matches or exceeds the accuracy of folder nodes on most systems. Extending a directory assignment is also different from identifying files that depart from it. Comparing FM, FFM, and FD on the directory baseline's errors helps assess this distinction (Section~\ref{sec:directory_errors}), but does not isolate architectural exceptions from errors caused by missing local supervision.
 
Lucene and HDF have pure directories under the reference mapping, so their baseline errors do not reflect conflicts between directory and module membership. They may instead arise from directories without labeled examples, although the table does not establish this. FFM recovers most baseline errors on Lucene and half on HDF, but only about a fifth on A.UML, whose directories are also pure. Directory purity therefore does not ensure that folder nodes recover baseline errors.
 
Bash and HDC have mixed directories. On baseline errors, FFM is similar to FM on Bash and less accurate on HDC. JabRef further illustrates why overall gains are insufficient: adding folder context raises overall accuracy while lowering accuracy on baseline errors. These comparisons do not establish whether the affected files depart from their directory's majority module.
 
The directory rule serves as a reference point for interpreting the learned models. Where directory organization closely follows the architecture, it already reproduces most of the mapping. On most evaluated systems, the added modeling complexity therefore brings little accuracy over the rule; where directories are less reliable, content and dependencies could be complementary signals, which these systems cannot show. Evaluating the additional value of a learned mapper therefore requires separating files in directories without labeled examples from files whose module differs from their directory's majority module. The present analysis does not establish how reliably the compared models handle the latter. A risk is that a model given folder information reproduces the directory assignment, including its errors. The low accuracy on baseline errors on most systems is consistent with this, but we did not test it.
 
RQ2 uses HGT to model the node and relation types of the heterogeneous variants. Although HGT gains the least from neighbor access in RQ3, its median macro-F1 gap to GAT is only 1.2 to 2.4 points, far smaller than the folder gains in RQ2. This suggests that predictor choice alone is unlikely to explain those gains, but whether they persist with GAT on the heterogeneous variants remains untested.

\subsubsection*{Dependency Neighbors and Aggregation Direction}
The benefit of dependency neighbors depends on how the predictor aggregates them. HGT gains least, while GAT achieves the highest median macro-F1 with every representation under undirected aggregation, although differences between predictors are small relative to variation across systems. GAT and HGT differ in their attention formulations and parameterizations, so the comparison does not isolate why GAT performs better. These findings concern the evaluated file-level predictors, not the folder- and member-aware configurations or the usefulness of dependency types in general.

The preferred aggregation direction appears to depend more on the system than on the predictor or representation, although the pattern is not uniform across metrics. This suggests that neither direction is consistently preferable across systems. Agreement across configurations and models describes this consistency rather than providing independent evidence, since the comparisons share systems and splits.

Undirected aggregation adds reverse edges, so the comparison does not isolate propagation direction from neighborhood size. A reversed-edges-only setting would help distinguish these effects and remains for future work. With Node2Vec, directed aggregation lowers median macro-F1 for all three predictors. Since its vectors were learned on an undirected graph, this may reflect a mismatch between the neighborhoods encoded during initialization and those used during prediction, but this explanation remains untested.

\subsubsection*{Connectivity and Neighbor Information}
Connectivity describes how much neighboring context is available, measured here by average node degree, while homophily describes whether linked files share a module. Few neighbors limit the context available to shallow message passing, whereas Node2Vec can encode more distant context through random walks. Limited connectivity may therefore constrain the benefit of additional aggregation even when the initial structural representation remains useful.

Several results are consistent with this interpretation. With Node2Vec and undirected aggregation, no predictor changes significantly on Bash and HDC, the two lowest-degree systems. In FM and FFM, dependencies between member nodes require two layers to reach file predictions; we therefore examined whether the macro-F1 change from one to two layers relates to average degree. Exploratory Kendall’s $\tau$ analyses~\cite{kendall} show positive associations in FFM across all three representations, but in FM mainly with Word2Vec.

Connectivity may also help explain the effect of aggregation direction. T.Mates and SH-3D combine low homophily with high average degree, gain most from file-level message passing with Node2Vec in RQ2, and favor directed aggregation in RQ3. Bash and HDC favor undirected aggregation, as does HDF, which has low homophily but much lower average degree than T.Mates and SH-3D. Reverse edges may supply missing context in sparse neighborhoods but introduce additional cross-module context in dense, low-homophily neighborhoods. This mechanism remains untested: the ten-system comparison cannot separate connectivity from homophily, system size, or label scarcity.

\subsubsection*{Implications for Evaluation}
Evaluation should establish what the input representation already provides, then isolate access to neighborhood information within a fixed predictor. Comparing a GNN model with an MLP changes both the predictor and its access to dependency structure; enabling and disabling neighborhood information within the same predictor tests whether that access helps. The same applies to folder information: a comparison of graph variants should include a model that receives that information directly.

Micro-F1 and macro-F1 should be read together, since correctly mapping more files does not necessarily improve performance across modules. For tools intended to identify architectural exceptions, aggregate scores should also be accompanied by performance on files whose module differs from the majority module of their directory. These comparisons help distinguish the contributions of representations and neighbor processing from gains that mainly reproduce directory organization.

The intended use also matters. If mapping supports code reorganization, the existing directory structure may be something to reconsider rather than reproduce. Strong performance based on that structure does not establish which information would remain useful when the organization changes. The present study does not test this setting, but motivates evaluating information sources against the intended task rather than treating any representation or predictor as generally preferable.

\section{Related Work\label{sec:work}}

Architecture recovery and code-to-architecture mapping both infer a system's modular structure from implementation artifacts, such as static dependencies, code semantics, and directory organization. Recovery produces a decomposition without a reference architecture, while mapping assigns entities to the modules of a given one. We evaluate mapping and draw on recovery research for representations of dependencies, lexical content, and project organization.

Recovery techniques have historically been built around one dominant signal: dependency graphs, partitioned by search-based optimization~\cite{bunch,bunch_sahc_nahc,dagc,wca,mca_eca} or clustering~\cite{cct,hcc_2019,limbo,fca,neighborhood_tree_2019,gma_2021}, identifiers and comments~\cite{arc,zbr,risi2012fold,kargar2017semantic}, or file names and paths~\cite{file_clustering}. Each signal is noisy in isolation, since shared utilities introduce cross-module edges and reused terminology mixes entities from many modules, so hybrid methods combine sources~\cite{sc_misra,escrc,nsga3,sadat2019multi,ensemble_recovery,evol,sade,sarif}.

Mapping began with orphan adoption~\cite{tzerpos1997orphan} and the attraction functions of HuGMe~\cite{christl2005equipping,christl2007automated}, and later varied the signal and the learner: textual similarity~\cite{bittencourt_IR}, supervised classifiers~\cite{bibi2016supervised}, and semi-supervised Naive Bayes combining lexical and dependency-derived information~\cite{olsson2019semi,olsson2022automatically}. Text-based approaches compare classifiers for module assignment~\cite{florean2021textclassifierscomparison}, recommend mappings from natural-language architecture descriptions~\cite{InMap}, or integrate package- and class-level granularity~\cite{sinkala2023integrated}. More recent work uses TF-IDF, GloVe, and LLM representations~\cite{johansson2024mapping}, extracts architectural concepts from documentation and code~\cite{fuchss2025enabling}, or prompts LLMs to map implementation units to a reference architecture, which faces context-size limits and repeated processing costs on large codebases~\cite{rukmono_deductive}. Johansson and Caporuscio map functions and files to textual module descriptions with pre-trained embeddings and find files classified more reliably than functions, with performance associated with vocabulary overlap and class separability~\cite{johansson2025mapping}.

Representation-learning work on recovery encoded one or two sources at a time. NEGAR clusters Node2Vec embeddings of the dependency graph alone~\cite{negar}. Jabeen et al.~\cite{structsar} study dependencies alone and with folder organization, comparing random walk-based methods and variational graph autoencoders. GAER~\cite{gaer}, a graph autoencoder, and ARL~\cite{arl_2026}, a contrastively trained GAT, each fix folder and identifier tokens into one encoding without comparing alternatives. For mapping, GNNs were evaluated on homogeneous and dependency-type-aware graphs without folder or member nodes and without separating graph contribution from feature contribution~\cite{jabeen2025graph}. Its extension combines Word2Vec identifier embeddings and binary bag-of-words representations of folder path tokens with dependencies in one model~\cite{c2a_mapping}.

These approaches motivate our distinction between representing an information source and using it during prediction. Text-based mapping reports weaker results for functions than for files~\cite{johansson2025mapping}, but does not examine whether member information helps as context for the file. Our comparisons span lexical, structural, and contextual inputs but retain differences in their training procedures and feature content, so the matched dependency controls and directory-error analyses assess specific design choices and do not turn the broader comparison into an isolated ranking of information sources.

\section{Conclusion\label{sec:conclusion}}

This study examines how code text, static dependencies, folder organization, and member-level information contribute to code-to-architecture mapping on ten systems. The findings show that mapping performance depends not only on which information is available, but also on how it is represented and used.

Encoding dependency information in file representations improves mapping beyond the evaluated lexical and pretrained code representations. Node2Vec and dependency-guided fine-tuned UniXcoder outperform Word2Vec on most systems, and fine-tuning improves UniXcoder over its zero-shot counterpart on nearly all systems. However, neither Node2Vec nor fine-tuned UniXcoder is consistently best across systems.

Folder nodes produce the largest and most consistent gains within the HGT variants, but a directory rule using the same labeled files reaches similar accuracy on most systems. These gains do not consistently translate into better predictions on files the rule assigns incorrectly. Member nodes provide no consistent improvement, and their effects cannot generally be separated from changes in feature construction and placement. These structural findings are specific to HGT; whether they persist with other predictors remains untested, particularly given HGT's smaller gains from dependency neighbors in the file-level comparison.


Keeping the input representations fixed while enabling and disabling access to dependency-neighborhood information shows that neighbor aggregation can complement representations that already encode dependencies. Undirected aggregation raises the median scores for all three predictors with every representation. GAT achieves the highest median macro-F1, while HGT gains the least. The better aggregation direction varies between systems, although the experiments do not isolate propagation direction from neighborhood size. 

Evaluation should therefore distinguish information already encoded in the representations from the contribution of neighborhood access. The findings support assessing these contributions for the intended mapping task, rather than treating any representation or predictor as generally preferable.

\section{Threats to Validity\label{sec:threats}}

\parg{Generalizability:} We evaluate ten open-source systems in Java, C, and C++, each with one reference architecture. The findings may not extend to other systems or alternative architectural decompositions. The study is transductive: representation learning and graph processing can use unlabeled test nodes and their edges. It therefore does not establish performance on newly arriving files outside the observed graph or on maintaining a mapping as the system evolves. Other information sources, including change history and dynamic dependencies, are outside the evaluated scope.

\parg{Dependencies and reference mappings:} Dependencies are extracted using static analysis, which may miss or misresolve dependencies. Preprocessing and build configuration can also affect the dependencies available for analysis. Because predictors that use neighbors depend on the extracted graph, such errors can affect their predictions. Models with neighbors enabled and disabled are trained separately. Their comparison therefore measures the effect of training with access to neighbor information, rather than removing neighbors from a fixed trained model.

The analyzed source code may not match the version a published mapping describes. Several benchmark mappings were created years before the source versions used here were obtained, and the files included in a system can depend on its build configuration, so the analyzed file set may differ from the one the mapping covers. In older systems, architectural drift may also weaken the correspondence between a file and its assigned module.

Files can plausibly belong to more than one module, and annotators may assign them differently. Because the initial labeled set is sampled from the same mapping used for evaluation, an incorrect assignment can both mislead the model during training and penalize an architecturally plausible prediction.

\parg{Experimental variation:} We use 100 runs per configuration. These runs reuse the same systems and can include the same files, so they are not independent samples. With this many runs, small differences can reach statistical significance, so we report results per system and include effect sizes to distinguish the magnitude of a difference from its significance. The comparisons were not fixed in advance, so the analyses are exploratory and may favor patterns specific to this benchmark.

The runs use different initial labeled sets, but the contribution of stochastic model training to the observed variation was not assessed separately. Input representations were generated once per system and reused across runs, so variation arising from their generation was not assessed. The seeds governing model initialization and training were not retained, limiting exact reproducibility. Cliff's $\delta$ treats the paired scores as two independent groups, so it describes the separation of the two score distributions and not the paired differences.

\parg{Interpretation of results:} Performance measures agreement with the reference architecture, not whether a prediction is the only architecturally reasonable assignment. Folder organization may reflect the same decisions used to define that architecture, so strong directory-based predictions do not by themselves demonstrate recovery of architectural intent. The directory-error analysis applies only where the directory baseline makes errors, which excludes C.Img, SH-3D, and T.Mates in most or all splits, and it does not isolate files whose module differs from the majority module of their directory.
Message-passing depth was varied only for HGT in RQ2, with one and two layers, so the results do not show how deeper models or other predictors respond. It reports accuracy only, so it does not show how performance differs between small and large modules.

Relationships between performance and structural properties are reported as associations, not causal effects, since the benchmark does not allow these properties to be separated from one another or from system size and label availability. The fine-tuning gain is that of the whole dependency-guided procedure, since no alternative adaptation objective was evaluated, so it is not attributed to dependency topology alone.

\section{Conclusion\label{sec:conclusion}}

This study examines how code text, static dependencies, folder organization, and member-level information contribute to code-to-architecture mapping on ten systems. The findings show that mapping performance depends not only on which information is available but also on how it is represented and used.

Representations that encode dependency information perform better than the evaluated lexical and pretrained code representations. Node2Vec and dependency-guided fine-tuned UniXcoder outperform Word2Vec on most systems, and fine-tuning improves UniXcoder over its zero-shot counterpart on nearly all systems. However, neither Node2Vec nor fine-tuned UniXcoder is consistently best across systems.

Folder nodes produce the largest and most consistent gains within the HGT variants, but a directory rule using the same labeled files reaches similar accuracy on most systems, and folder paths supplied as file features match or exceed folder nodes on most systems. These gains do not consistently translate into better predictions on files the rule assigns incorrectly. Member nodes provide no consistent improvement with one or two HGT layers, and their effects cannot generally be separated from changes in feature construction and placement. These structural findings are specific to HGT; whether they persist with other predictors remains untested, particularly given HGT's smaller gains from dependency neighbors in the file-level comparison.

Keeping the input representations fixed while enabling and disabling access to dependency-neighborhood information shows that neighbor aggregation can complement representations that already encode dependencies. Undirected aggregation raises the median scores for all three predictors with every representation. GAT achieves the highest median macro-F1, while HGT gains the least. The better aggregation direction varies between systems, although the experiments do not isolate propagation direction from neighborhood size. Evaluation should therefore distinguish information already encoded in the representations from the contribution of neighborhood access. The findings support assessing these contributions for the intended mapping task, rather than treating any representation or predictor as generally preferable.

\parg{Future work.} Future research could separate which aspects of graph context account for the observed differences. Undirected aggregation changed both propagation direction and neighborhood size, and member nodes changed both graph structure and feature placement, so comparing incoming, outgoing, and combined neighborhoods at matched sizes, and adding member nodes while preserving each file's own features, would show which change matters. Another direction is configuration selection on unfamiliar systems. Homophily, which helped interpret the system differences, requires reference module assignments, so selection rules based on properties observable in the dependency graph alone could be developed on some systems and evaluated on others. Finally, a model trained on one version could be evaluated on new and changed files in later versions without retraining, to test whether the learned information supports mapping as systems evolve.
