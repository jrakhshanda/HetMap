\section{Introduction\label{sec:intro}}

Maintaining a software architecture requires knowing which implementation elements belong to its modules. That correspondence can become difficult to maintain as a system grows: new files introduce responsibilities and dependencies, while architectural documentation may lag behind the implementation. Code-to-architecture (C2A) mapping addresses this problem by assigning source files to the modules of a reference architecture. The resulting mapping supports reflexion modeling, which compares implementation dependencies with architectural relations to identify divergence~\cite{reflexion1}. It therefore connects the modular decomposition used to reason about a system~\cite{parnas1972,clements2003} to the code in which that decomposition is realized.

Several sources of evidence can support a mapping. Identifiers express domain concepts and implementation roles. Contextual code representations capture information from declarations and operations. Static dependencies locate a file among other files with which it interacts, while directories record how developers organize the project~\cite{sarif,negar,garcia2013}. These sources need not agree: a utility may depend on several modules, terminology may be shared across responsibilities, and a directory may contain files assigned to different architectural modules.

The usefulness of an information source also depends on how it enters a predictor. A dependency embedding can encode graph structure before a classifier sees a file. Propagating over dependencies then supplies a second form of access to related files, with its own assumptions about direction, relation types, and aggregation. A gain from the embedding does not establish that this additional propagation will help. Similarly, a folder-aware model can improve overall agreement with a reference architecture while losing correct predictions for files that depart from a directory-based assignment. These distinctions motivate studying both the information supplied to a model and the changes caused by the way it processes that information.

Prior graph-based representation learning work on architecture recovery represents these sources in different ways, from Node2Vec random walks on the dependency graph~\cite{negar} and graph attention with diffusion-based rewiring~\cite{structsar} to a graph autoencoder over identifier and folder tokens~\cite{gaer}. For mapping, prior work combines lexical and organizational features with dependencies in a single graph neural network~\cite{jabeen2025graph,c2a_mapping}. Because all signals enter that model together, it remains unclear how much each contributes and how it should be represented.

We examine this question through C2A mapping, formulated as a classification problem in which each file is assigned to one module of the reference architecture. We work in a transductive low-label setting, where a small sample of files covering every module is already mapped, and the model infers the remaining assignments. The model is trained on the labeled files alone. This setting allows us to examine how file representations and graph relations contribute under limited supervision.

Our evaluation uses ten Java, C, and C++ systems and covers lexical Word2Vec, structural Node2Vec, and contextual UniXcoder representations. These serve as inputs to a graph-free neural baseline, to a Heterogeneous Graph Transformer (HGT)~\cite{hgt}, and, in the dependency comparison, to a neighbor MLP and a Graph Attention Network (GAT)~\cite{gat}. The heterogeneous configurations contain file nodes and, where applicable, folder nodes and one aggregate member node per file. They vary both the context available to a file and where feature content is stored. Alongside these configuration comparisons, we run controlled comparisons that change one design choice while holding the features, labeled splits, initialization, and training budgets fixed within each comparison.

The configuration results motivate two complementary analyses. A directory analysis distinguishes errors corrected by a model from previously correct predictions that it makes incorrect. A dependency analysis compares ways of using dependency neighbors on all ten systems, enabling and disabling neighbors and aggregating them along the dependency direction or in both directions.

We address three research questions:
\begin{itemize}
    \item \textbf{RQ1.} How does mapping performance vary across lexical, structural and contextual file representations?
    \item \textbf{RQ2.} How does message passing over file dependencies and through member and folder nodes affect mapping performance for each representation?
    \item \textbf{RQ3.} How does using dependency neighbors change mapping performance, and how do the predictor and aggregation direction affect this change?
\end{itemize}

The results show that dependency information supports C2A mapping through both file representations and neighbor context, but the benefit of neighbor context depends on how it is processed. Folder organization yields the largest gains, largely reflecting information already available through a directory rule. Aggregate improvements can conceal regressions on individual files. These findings clarify how input signals and their use by a predictor affect C2A mapping across the ten systems studied\footnote{\label{fn:code}Code and data are available at \url{https://github.com/sse-lnu/hetmap}.}.
